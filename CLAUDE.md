## Project Overview

**Tabac** ("Ma Cave à Tabac") is a Progressive Web App (PWA) — Single-Page Application (SPA) architecture — for managing a personal pipe tobacco collection and pipe inventory. It is a French-language application built with Vite + React 19 + TypeScript. `App.tsx` is the root component and state owner; business logic lives in `src/hooks/`.

The Curator UI (`src/CuratorApp.tsx` + `src/views/curator/` + `src/components/curator/`) is the only renderer. `App.tsx` owns global state + hooks and renders `<CuratorApp />` (or `<CuratorTermsGate />` before the user accepts terms).

## AppContext Pattern

All views read App state via the React Context, avoiding prop-drilling:

```ts
// src/AppContext.tsx — l'ESQUISSE, pas le fichier : ~400 clés typées y vivent.
import React from "react";
export interface AppCtxType {
  t: (key: string, n?: any) => string;
  nav: (view: string, ...rest: any[]) => void;
  data: AppData;
  /* …environ 400 clés, chaque callable REQUIS et typé… */
}
export var AppCtx = React.createContext<AppCtxType>({ /* graine peuplée */ } as AppCtxType);
export function useAppCtx(): AppCtxType { return React.useContext(AppCtx); }
```

**Ce bloc a longtemps montré `export type AppCtxType = Record<string, any>` et une graine vide `{}`, ce qui contredisait mot pour mot le paragraphe « `AppCtxType` est entièrement typé » vingt lignes plus bas.** Il datait d'avant le typage ; personne ne l'a relu en écrivant l'anti-régression qui le dément. Une esquisse a le droit d'abréger — elle n'a pas le droit d'annoncer le contraire de la règle qu'elle illustre.

In `App.tsx`, all state and functions are bundled into a single context value object (`appCtx`) and provided at the root:

```tsx
var appCtx = { data, view, nav, t, xl, lang, weightUnit, /* ... all state & functions */ };
return h(AppCtx.Provider, { value: appCtx }, /* views router */);
```

In views:
```tsx
const { data, nav, t, weightUnit } = useAppCtx();
```

**Single `appCtx` consumed by every Curator view.** `data`, `nav`, `t`, `xl`, `lang`, all `*Store` actions, `pickJarLot`, `lotAgingStatus`, tasting actions, AI actions, Drive actions, etc. When adding a new ctx key, expose it in the `appCtx` object built in `App.tsx` (currently around lines 2660-2970 — the range drifts with every App.tsx edit, so search for `var appCtx = {` rather than trusting the numbers). Missing exposure is the most common source of "button does nothing" bugs (the destructure silently yields `undefined` and the guarded handler short-circuits).

**`AppCtxType` is fully typed — keep it that way (anti-regression).** `src/AppContext.tsx` is no longer `Record<string, any>`: every **callable** (store actions, setters, tasting/gdrive/ai/export functions) is typed and **required** (`(...args: any[]) => void|any` at minimum, real signatures for `t`/`xl`/`nav`/store CRUD), every **primitive/pref** has its base type, and `data`/`dataRaw` are `AppData`. Two invariants when you add or touch a ctx key: **(1)** add it to `AppCtxType` with a real type (a new callable is `required`, not `?: any` — required keys never break tests or the seed because both are cast, see below) AND expose it in App.tsx's `appCtx` — the typecheck now flags the read site if you forget either; **(2)** the `createContext` seed and the direct-`AppCtx.Provider` test literals are deliberately cast (`as (unknown as) AppCtxType`), which is what lets required keys stay churn-free — don't "fix" those casts by trying to enumerate every key. The **~34 remaining `?: any`** keys (working-copy form objects, refs, blank `B*` templates, polymorphic `tasting`/`stats`/`updateStatus`/`*Confirm` unions) are a DELIBERATE, documented tail — see the header comment on `AppCtxType`. Do NOT bulk-convert them to precise types; typing a working-copy form surfaces false-positive shape errors for no safety gain. Type one of them only if a concrete bug motivates it.

**`nav()` MUST NOT reset edit IDs or form state (a hard invariant).** The edit handlers in every detail view follow the pattern:

```ts
setXxxForm(Object.assign({}, BX, item));
setEditXxxId(item.id);
nav("editX");
```

React batches setStates in a single event handler and applies them in order. If `nav()` resets `setEditXxxId(null)` (or `setXxxForm({})`), the user's intent is silently wiped — the edit form loads but `editXxxId === null` at save time, so the store's `updateXxx` `.map()` matches nothing and the modification is lost. **The clean lifecycle is**: set by the edit handler → cleared by the form's `cancel()` or by the store's `updateXxx()` / `addXxx()` success path. Nothing else, including `nav`, should touch them.

**The OTHER end of that lifecycle: the "+" button must BLANK the working copy, and for 150 releases it did not.** The rule above is right and stays; its consequence is that a form left any way OTHER than `cancel()` keeps its working copy loaded — and that is the ordinary way to leave one, because a form the user has not modified is CLEAN, so `useUnsavedFormGuard` lets a system-back or an edge-swipe through without a word. The next `nav("addT")` then opened « Un nouveau tabac » over the previous tobacco's fields, photo, notes and rating. **It is not cosmetic**: `addTobacco` does `uid: source.uid || newUid()` and re-stamps only lots that LACK an id, so the new row inherits the edited entity's **`uid`** — the cross-device merge identity `resolveMergeMatch` matches on FIRST — and duplicates its lot ids **globally**, which is exactly what `useTrashOps` and the 30-day sweep filter on. Three invariants fire at the next `save()` (`tobacco-uid-unique`, `lot-id-unique-global`, `lot-uid-unique`); `addPipe` additionally carries `maintenance` and `photos`, `addAccessory` the same uid. **What identifies it as an oversight rather than a decision: the SAME handler in `InventoryListView` already did it right for the wishlist** (`setWishForm({...BW}); setEditWishId(null)`) — that form is an overlay and had to — while the three view-based forms never got it, and `wishToInv` builds from `BT` with an explicit field allowlist for the same reason. The three lists now each carry an `openAddTobacco` / `openAddPipe` / `openAddAccessory` used by BOTH their "+" and their empty-state CTA, so the two doors cannot drift. `nav()` is untouched — the fix belongs at the button, not in the store (a store that ADOPTS a source uid is correct for a genuine import) and not in `nav` (that is the invariant). **Note the inversion this leaves recorded: the DIRTY path was always safe** (the guard's « Quitter sans enregistrer » calls `cancel`); the CLEAN one was not. Locked by `addFormStartsBlank.test.tsx`, probed per view.

## Security

### Content Security Policy (CSP)

A `<meta http-equiv="Content-Security-Policy">` tag is present in `index.html` (root level, second line after `<meta charset>`). **If you add a new external API endpoint or CDN script, you must update the CSP accordingly.**

Key directives:
- `connect-src`: whitelisted domains are `api.anthropic.com`, `api.openai.com`, `generativelanguage.googleapis.com`, `www.googleapis.com`, `accounts.google.com`, `oauth2.googleapis.com`, `api.dropboxapi.com`, `content.dropboxapi.com` (the last two added with the Dropbox provider), `nominatim.openstreetmap.org` (session-location reverse geocoding, see geo.ts). The image proxies `corsproxy.io` / `api.allorigins.win` were **removed** (local-photos-only). Any fetch to an unlisted domain will be blocked.
- `frame-src`: `https://www.openstreetmap.org` only — the per-session OSM map iframe (the geolocation work). `form-action`: `'self' https://accounts.google.com`.
- `script-src`: `'self'`, `cdnjs.cloudflare.com`, `accounts.google.com`, `apis.google.com`. No `'unsafe-inline'` — the built HTML has no inline scripts.
- `style-src`: `'self'`, `'unsafe-inline'`, `accounts.google.com` — needed for inline `<style>` tags.
- `font-src`: `'self'` only (fonts are self-hosted under `public/fonts/`). Do NOT re-add `fonts.gstatic.com`.
- `frame-ancestors 'none'`: **INERT, and kept deliberately — this line used to claim it "prevents clickjacking via iframes" and that was FALSE.** CSP Level 3 §3.3 requires a user agent to REMOVE `frame-ancestors` (with `report-uri` and `sandbox`) from a policy delivered by a `<meta>` element, so no browser has ever honoured it here — **Chromium says so in the console, verbatim: *"The Content Security Policy directive 'frame-ancestors' is ignored when delivered via a `<meta>` element."*** The header form would work and the app cannot send one: GitHub Pages serves static files with no header customisation and there is no `_headers` / `netlify.toml` / reverse proxy in front of `t-cellar.app`. It STAYS because it is the correct directive the day this is served behind something that can send headers, and because deleting it invites the next reader to "add clickjacking protection" and put it straight back — so index.html carries a comment saying it is inert and naming the real defence. **THE REAL DEFENCE IS `src/utils/frameGuard.ts`, which refuses to RENDER a framed document.** See that module for the risk analysis; the short version is that an attacker cannot READ a cross-origin frame, so nothing leaks, but they can UI-redress a frame showing the visitor's REAL cellar — and while the reset and « Vider la corbeille » sit behind `window.confirm` (browser chrome, not overlayable) and an ordinary delete is a soft-delete with a 30-day trash, the cloud-newer banner's « Restaurer » is a genuine one-click `stageImport(…, {autoApply:"replace"})` with no confirmation (recorded deliberately in `docs/integrations.md`). **"Do not render" is the defence and the bust-out is only best-effort** — MEASURED in a real cross-origin frame, Chromium refuses it (*"Unsafe attempt to initiate navigation for frame with URL …"*), which is exactly the drive-by case that matters; the notice's link carries `target="_top"` and works because a user CLICK grants activation. The guard lives in `main.jsx` pre-mount, NOT as an inline script (the CSP is `script-src 'self'` with no `'unsafe-inline'` — our own policy would block it, the boot-strings reasoning), and it gates the mount AND the service-worker registration (installing the offline machinery for a page the user never chose to open is not something a refused document should do). Its six strings live in the SAME `BOOT` table as the boot shell — one pre-mount language axis, already covered by doc:check gate 15 (`docs/checks.md`); a second map is the shape a whole release was spent removing. Verified end to end in Chromium with two static servers on different ports (top level boots normally, cross-origin frame shows only the notice); probed four ways, each reddening.
- `upgrade-insecure-requests`: forces HTTP sub-resources to HTTPS.
- `object-src 'none'`: no browser plugins.
- `base-uri 'self'`: prevents `<base>` tag injection.
- `worker-src 'self'`: service worker only from same origin.
- `img-src 'self' data: blob: https:`: allows all HTTPS image sources (user-provided tobacco/pipe images can come from any domain).

### OAuth CSRF

The `gdrive-state` localStorage key holds a random token set before the OAuth redirect. On callback, the app rejects the response if either the stored state or the returned state is absent or mismatched (`!st || !expectedSt || st !== expectedSt`). Never weaken this guard to `&&`.

The pending OAuth action (`gdrive-pending`) is validated against a whitelist (`"save"`, `"restore"`, `"reconnect"`, `"list"`, `"autosave"`, `"restore-cnb"`, `"cat-save"`, `"cat-restore"` — the same eight invariant #20 enumerates) before dispatch. Any other value is ignored.

### OAuth flow — iOS standalone vs. non-iOS

**Non-iOS (popup):** uses Google's `gsi/client` `initTokenClient` (popup mode). Officially supported by Google for client-side apps. No code exchange or client_secret needed.

**iOS standalone (redirect):** uses `window.location.replace()` with `response_type=token` (implicit grant). This navigates within the PWA webview — `initTokenClient` always opens a popup which leaves the PWA, causing the callback to never fire (stuck on "Connexion..."). PKCE (`response_type=code`) also fails because Google **Web Application** OAuth clients require `client_secret` for the token exchange, which cannot be embedded in client-side code. `response_type=token` is therefore the **only viable option** for this combination (iOS standalone + Web Application OAuth client + no backend). A cryptographically-random CSRF state (from `pkceGenerateVerifier()`) is stored in `gdrive-state` before the redirect and validated on return.

**Do NOT "fix" the iOS standalone flow to use PKCE or `initTokenClient`** — both have been tried and both fail. The token is returned in `#access_token=...` and processed by the App.tsx hash handler. PKCE helpers (`pkceGenerateVerifier`, `pkceChallengeFromVerifier`) are kept for the CSRF state generation and their test suite.

### Import hardening

- `_imageData` on Drive restore (`doGdriveConfirm`) and JSON import (`doImportFile`): keys must start with `local-photo-`, values must match `/^data:image\/(jpeg|jpg|png|webp|gif);/`. Anything else is silently discarded before touching IndexedDB.
- ID counters (`nxT/nxW/nxP/nxA/nxJ`) are clamped to integers ≥ 1 in `migrateData` on every load and import.

### SSRF mitigation

`isSafeExternalUrl(url)` in `src/utils/imgCache.ts` is a pure URL-safety predicate (no network — the app makes no external image fetch at all). It's used by `safeBgUrl` and the lightbox src guard. It rejects non-HTTP(S) protocols, `localhost`/`127.x`, RFC-1918 ranges (10.x, 172.16–31.x, 192.168.x), link-local (169.254.x), and bare hostnames without a dot.

`safeBgUrl(url)` (same module) wraps a URL safely for use in CSS `background: url(...)`. Same SSRF guard plus a CSS-metacharacter reject list (`"`, `'`, `(`, `)`, `\`, `;`, whitespace). Every Curator view that interpolates a URL into a `background` style uses `safeBgUrl`. Tests in `src/__tests__/safeBgUrl.test.ts` lock this in (26 cases). (The old `dlImg.test.ts` was removed with `dlImg`.)

## Dead code hygiene

`npm run prune` runs **knip** (`knip.json`) to surface unused exports, files, types and dependencies. The check is fast (~1s) and configured to:
- Treat dead **runtime dependencies** as errors (CI gate)
- Treat dead **devDeps, exports, files, types** as warnings (developer signal, not blocker)
- Ignore `eslint-rules/string-locale-compare.cjs` (uses an indirect `module.exports.rule = …; Object.assign(module.exports, module.exports.rule)` pattern knip can't follow — it needs that shim because the rule *used to be* that file's default export). **`no-dynamic-index-plain-map.cjs` had copied the same shim with no such history**, so it was flagged too; rather than add a second ignore, the file was converted to the plain `module.exports = { meta, create }` shape the other ten rules use — nothing had ever read `.rule`. Prefer that fix over an ignore entry: an ignore also hides a genuinely dead export in the same file.
- `ignoreDependencies: ["playwright-core"]` — the two opt-in browser checks `require()` it deliberately without it being a dependency (see `i18n:layout`); without this, knip's `dependencies: "error"` rule failed the run. Scoped to that one package, so a genuinely-unlisted import is still an error.
- Use `ignoreExportsUsedInFile: true` so internal "exported but never imported externally" patterns (like `Curator*Banner` components in `Overlays.tsx`, consumed by `CuratorOverlays` in the same file) are silent

**It is one of the per-build gates** (see "After every change") — must exit 0. Current baseline: **exit 0, zero findings** (restored — it had been failing ever since the first `playwright-core` require landed, precisely because it was NOT a gate and nobody re-ran it; the "zero warnings" line stayed in the doc for nine releases. **A claim about a tool's output is only true while someone runs the tool** — if you assert a baseline here, run the command in the same commit).

## Service Worker Notes

- Cache name: `cave-tabac-v1-0-1` (current). In `public/sw.js`. See bumping rules below.
- Cached assets: the root `./`, `index.html`, `help.html`, `reset.html`, `changelog.html`, `privacy.html`, `manifest.json`, `icon-192.png`, `icon-512.png`, `icon-512-maskable.png`. `licenses.html` is NOT pre-cached (served network-first like every other page). No CDN scripts — React 19 is bundled by Vite. Self-hosted woff2 fonts are fetched once and served from the SW cache on subsequent loads (cache-first per the default fetch handler).
- **Never cached** (always fetched from network): `api.anthropic.com`, `api.github.com`, `api.openai.com`, `corsproxy.io`, `allorigins.win`, `googleapis.com`, `accounts.google.com`, `gstatic.com`. Bypass check parses the URL hostname and matches exact host or `*.host` suffix — the previous `indexOf` form was flagged by CodeQL as an incomplete URL substring sanitization.
- **`self.clients.claim()` is intentionally absent** from the `activate` handler. This ensures the new SW does not take over open pages mid-session — activation only occurs via `doUpdate()` (`SKIP_WAITING` → `location.reload()`), which is called automatically after the 10s countdown banner or on explicit user action in Settings.
- **`reg.update()` must NEVER be called automatically** (no timers, no visibility-change handlers). Calling it downloads a new SW silently; once that SW enters "waiting", the browser activates it automatically the next time all clients close (e.g. user closes and reopens the app), bypassing user consent. Version detection uses `checkVersion()` only (fetches `version.json` from network — no SW installation side-effect).
- **CRITICAL — automatic update mechanism**: Any change to `sw.js` causes the browser to install a new SW in the background. That SW enters "waiting". The next time the user closes all tabs and reopens the app, the browser activates it automatically — the user experiences this as an unwanted automatic update. This is standard browser behavior that cannot be prevented once a new SW is waiting.
- **HTML pages are network-first** (this used to say *navigation requests*, and the difference was the bug): `index.html`, `help.html`, `changelog.html`, `reset.html`, `privacy.html` are served network-first by the SW, so users always get the latest version when online, and there is NO need to change `sw.js` when these files change. **The branch used to key on `event.request.mode === 'navigate'`, which is true only for a browser NAVIGATION — while the in-app doc views (`DocPageView`, `HelpView`) read those same files with a plain `fetch("./help.html")`.** That is not a navigation, so it fell through to the cache-first branch and was served the copy captured at SW install, indefinitely. The claim above was therefore false precisely where users read the docs, and the workflow rule drawn from it ("documentation-only changes do NOT require bumping `APP_BUILD`") was false with it. The branch now keys on the URL being an HTML document (`isHtmlDoc`), which makes the documented behaviour the real one. **Same build: a 5xx no longer reaches the user when a cached copy exists.** A `fetch` that receives a 500 RESOLVES — it does not reject — so the handler's `.catch` never ran on a server error and the raw error page was returned while a good cached copy sat one line away. A GitHub Pages hiccup or a half-finished deploy broke an app that is otherwise fully offline-capable. **4xx still passes through on purpose**: a genuine 404 means the page is gone, and masking it with a stale copy would hide a deploy that dropped a file.

## Development Workflow

Always run quality checks before committing:
```bash
npm run typecheck   # Must pass (0 errors)

npm test            # Must pass (all tests green)
npm run lint        # Check for new lint errors (0 errors, some warnings acceptable)

```

**Why `prune` is a gate now.** It used to be a "re-run after any non-trivial refactor" tool, so nobody re-ran it: it had been failing (exit 1) while CLAUDE.md kept asserting a zero-warning baseline — nine releases of a red check that read as green in the docs. It costs **2.0 s**, the same as `doc:check`, so the only thing that kept it optional was habit. A check nobody runs is documentation, not a check.

### Service Worker versioning

**`APP_BUILD` in `src/constants.ts`**: bump on every build (controls the version display in Settings).

**`CACHE_NAME` in `public/sw.js`**: bump **ONLY** when one of these changes:
- `public/icon-192.png` or `public/icon-512.png`
- The SW logic in `public/sw.js` itself

**`manifest.json` was on this list and is deliberately no longer.** The rule predates the change that made `doUpdate()` purge unconditionally: it now unregisters every SW and deletes EVERY `caches.*` entry before the reload, and it runs on every build via the `version.json` flow. So a changed manifest reaches users through the ordinary build update — the SW reinstalls from scratch afterwards and re-fetches `CORE_URLS` from the network. Bumping `CACHE_NAME` for it is not merely unnecessary, it has a real cost the next bullet spells out: a byte-different `sw.js` makes the browser install a new SW in the background for everyone, which then activates on the next cold open, independently of the app's own update flow. (A user who never takes an update keeps a stale manifest — harmless: they keep a stale app too, and the manifest only supplies install-time metadata they have already consumed.) Editing `manifest.json` therefore needs the normal `APP_BUILD` bump and nothing more. Its shape is locked by the `manifest.json` block in `serviceWorker.test.ts` (valid JSON, installability fields, every declared icon present on disk, a maskable icon, and a `lang` naming a shipped UI language).

**NEVER bump `sw.js` for `src/` changes or `.html` file changes.** These files are served network-first — the user always gets the latest from the server without any SW change. Bumping `sw.js` unnecessarily installs a new SW that the browser then activates automatically when the user closes and reopens the app, which the user experiences as an unwanted automatic update.

### Editing documentation files (help.html, changelog.html, privacy.html)

These files live in `public/`. **Always fetch the current version from GitHub before editing**, using `mcp__github__get_file_contents` (owner: `yokyok71`, repo: `tabac`). This ensures edits are applied on top of the live server version, not a potentially stale local clone.

**Documentation-only changes do NOT require bumping `APP_BUILD`** in `src/constants.ts`. These files are served network-first — the browser always fetches the latest from the server. Only bump `APP_BUILD` when `src/` code changes.

#### `public/help.html` structural contract (in-app `HelpView` depends on it)

- **Language wrappers**: `<div id="sec-fr">…</div>`, `<div id="sec-en">…</div>`, and `<div id="sec-es">`, `<div id="sec-de">`, `<div id="sec-it">`, `<div id="sec-pt">` at the body level. Every section h2 must be a descendant of its language wrapper. `HelpView.SECTION_IDS` + `HELP_SECTION_IDS` (doc-check) list the per-language ids; doc-check validates every language whose wrapper is present. es/de/it/pt reuse the EN suffix (`es-install`, `pt-tobacco`, …); fr keeps its own (`fr-tabac`).
- **18 sections per language, each anchored by an h2 with a stable id** — the id ↔ key mapping is locked in three places that must stay aligned: `SECTION_IDS` in `src/views/curator/HelpView.tsx`, `HELP_SECTION_IDS` in `scripts/doc-check.cjs`, and the literal `<h2 id="…">` tags in `help.html`. If you rename, add, or remove a section id you must update all three at once.
  - FR ids: `fr-install`, `fr-concepts`, `fr-cycle`, `fr-catalogue`, `fr-tabac`, `fr-lots`, `fr-inventaire`, `fr-pipes`, `fr-wishlist`, `fr-acc`, `fr-journal`, `fr-ia`, `fr-stats`, `fr-sauvegarde`, `fr-maj`, `fr-depannage`, `fr-corbeille`, `fr-parametres`. (`install` sits at the top so new users land on the install procedure first.)
  - EN ids: `en-install`, `en-concepts`, `en-cycle`, `en-catalogue`, `en-tobacco`, `en-lots`, `en-inventory`, `en-pipes`, `en-wishlist`, `en-acc`, `en-journal`, `en-ai`, `en-stats`, `en-backup`, `en-updates`, `en-troubleshooting`, `en-trash`, `en-settings`.

- **Well-formed nesting in the body between h2s** — no stray `</div>` or unclosed tags. A malformed tag inside any list, table, or note will silently auto-close the wrapping `sec-fr` / `sec-en` div and eject every subsequent h2 to body level. The runtime parser is source-order-robust against this (it slices the raw HTML between h2 anchors), but the visual structure of the card breaks anyway and the cellar/journal/whatever stylings of the orphaned content may be subtly wrong.

**`npm run doc:check` enforces these invariants automatically.** It uses JSDOM to verify every id exists, is an `<h2>`, has non-empty text, and is a descendant of its language wrapper. The script fails (exit 1) on any violation — running before every commit catches the regression it was written for (a stray `</div>` on the "Sauvegarde auto Drive" `<li>` ejected the last 4 FR sections out of `sec-fr` and they rendered as 4 empty cards). If `doc:check` reports "h2 id=X landed outside `<div id="sec-Y">`", the offending tag is *before* X in the file — bisect by reading lines from the previous well-placed h2 forward.

The card UI also injects the help-body CSS (badges, notes, warns, flow diagram, table styling) from `HELP_BODY_STYLES` in `HelpView.tsx`. When you introduce a new CSS class in `help.html`, mirror its rule there or the new content will render unstyled inside the curator shell.

### Strict-TS promoted to main

The two strict flags — `exactOptionalPropertyTypes` and `noUncheckedIndexedAccess` — are now part of the main `tsconfig.json`. Background:

- `exactOptionalPropertyTypes` — `prop?: T` is distinct from `prop: T | undefined`. Catches code that spreads `undefined` into a field documented as optional.
- `noUncheckedIndexedAccess` — `arr[i]` and `record[key]` return `T | undefined` instead of `T`. Forces explicit handling of out-of-bounds / missing-key cases.

**History:** introduced as an opt-in (`tsconfig.strict.json`) with ~240 errors. Migrated incrementally — utils.ts, then App.tsx + InventoryListView, then useGdriveSync + useAiAutoFill + JournalView, then the full src/ production sweep (24 → 0), and finally the test files (168 → 0 via mostly `mock.calls[N]![M]` non-null assertions on RTL queries and Vitest mock state). The opt-in tsconfig and its `:strict` npm script were deleted — the main `npm run typecheck` is now the strict gate.

**For new code:** the patterns to internalize are
- `arr[i]` is `T | undefined` — capture with `const item = arr[i]; if (!item) return …;` OR assert with `arr[i]!` when the bound is provably satisfied.
- `prop?: T` in an interface means "may be absent OR `T`, NOT `undefined`". Don't pass `cb ?? undefined` to a `?:` prop — use conditional spread `...(cb ? { cb } : {})` or change the interface to `prop?: T | undefined` if the caller pattern requires it.

### Dead code discipline

`tsconfig.json` runs with `noUnusedLocals` + `noUnusedParameters`. Any local, parameter, or destructured field you stop using **must be removed in the same commit** — the typecheck refuses commits otherwise. This rule extends to:
- `import { x }` lines where `x` is no longer referenced.
- React state pairs `const [x, setX] = useState(...)` where neither side is read or both are dead.
- Destructured ctx vars (`const { x } = useAppCtx()`) where `x` is no longer used in the component.
- i18n keys in `src/i18n.ts` that no caller passes to `t("...")`.
- Functions/components/types exported but with zero call sites (verify with grep before deleting).

If you touch a file for an unrelated reason and notice obvious dead code, remove it in the same commit. Don't grow the dead-code backlog.

### changelog.html rules

- **NO CATALOGUE REFERENCES.** The changelog carried ~40 bullets about the catalogue across every language section — how many blends it held (1000 → 1160 → 1215 → 1225 → 1371), which families had been rechecked, where its buttons had moved. Every one of those became FALSE when the app stopped shipping a catalogue: a reader scrolling the history was told about a reference base they do not have. Removed on the user's instruction, and the rule stands: **do not announce the catalogue in the changelog.** Eleven entries were deleted outright, nine kept their other bullets and lost the catalogue ones, four were RETITLED (their heading named the catalogue beside a feature the entry still announces — pipe rest, wishlist sorting, geolocated sessions, the AI model refresh), and seven bullets were reworded. Three of those seven were FALSE POSITIVES worth knowing about: v1.1/1 and v1.2/5 used « Catalogue » as the OLD NAME OF THE INVENTORY TAB (they now say « Inventaire », which is also the accurate word), and v1.5/16's « les catalogues des fournisseurs » meant the AI vendors' model line-ups. Verified afterwards: zero lines matching `catalog|catálog|katalog` in any section, and all six sections lost exactly 40 `<li>`.
- **Six language sections** — `public/changelog.html` has one section per UI language: `<div id="sec-fr">` / `<div id="sec-en">` / `<div id="sec-es">` / `<div id="sec-de">` / `<div id="sec-it">` / `<div id="sec-pt">`, with a language toggle button identical to `help.html`. Every entry must appear in **all six** sections. (`doc:check` enforces only the `sec-fr` latest-build number, but the other four must stay in lock-step by convention.)
- **Features and important changes only** — include new features, new settings, significant UX improvements, and important behaviour changes (e.g. update mechanism changes). **Never include simple bug fixes** (display glitches, field resets, minor text corrections, etc.). **This is now a `doc:check` gate (12), because prose alone did not hold it.** **15 of the 25 entries** in the current version's section broke the rule and were deleted: photo framing, light-mode contrast, tap targets, bundle size, and six entries literally sub-titled `Correction`. Three patterns produced them, and they are the ones to watch for. **(a) The changelog was used as a build log, reverts included** — five consecutive entries were about the same photo frame, each undoing the last, so a user reading top-to-bottom watched an internal debate; another five do the same for light-mode contrast. *An iteration series is one decision, and usually one the user should not have to witness.* **(b) Audit-tool output was mistaken for UX work** — `theme:contrast` and `i18n:layout` phrase their findings in user language ("unreadable", "clipped"), and the diffs touch visible surfaces, so a contrast retune FEELS announceable. It is not: the user never noticed the old value and cannot act on the new one. **A build whose origin is a checker finding defaults to NO entry.** **(c) The checklist read as one-entry-per-build** while the exception lived two sections away — step 4 of the per-build checklist (`docs/checks.md`) now says the opposite first. The gate itself (`docChecks.checkChangelogIsFunctional`, tested in `docChecks.test.ts`) is deliberately split by certainty: a self-declared fix heading FAILS (the entry has already classified itself, no judgement needed), while display/implementation vocabulary only WARNS and needs two distinct terms — a real feature can legitimately mention colour, and an over-strict guard gets correct prose deleted. **When it fails, delete the entry — do not reword the heading.** In practice: `doc:check` enforces this by ALLOWING the latest changelog entry to lag behind `APP_BUILD` — a fix-only bump should leave the changelog untouched. The check still fails if the latest entry's build number is *higher* than `APP_BUILD` (no time travel).
- **Structure** — each build entry uses `<h2><span class="tag">vX.Y · Build N</span> Title <span class="date">Month YYYY</span></h2>` with `<h3>` sub-heading (Nouveau / New feature, Amélioration / Improvement, Important) and a `<ul>` of bullet points.
- **Version prefix in the tag (mandatory)** — the `class="tag"` chip MUST read `vX.Y · Build N` (the minor version, then `·`, then the build), NOT a bare `Build N`. Build numbers **restart at every minor version** (1.1 opened at **0** — the rule is that the counter restarts, not the digit it restarts on) (each minor version has its own second build…), so a bare `Build N` is ambiguous once the changelog spans several versions. The version prefix disambiguates at a glance. Do NOT repeat the version again inside the title text (the old `Build 1</span> v1.3 — Title` shape is retired — the first build of a version reads `<span class="tag">vX.Y · Build 1</span> Title`, version only in the tag). `doc:check` parses the latest build number with `/(?:v[\d.]+ · )?Build (\d+)/` so the prefix is tolerated but the `vX.Y · ` form is the required convention for new entries.

### End-of-task proactive suggestions

After every significant task (bug fix, feature, security change, release), always close with a short **"Et ensuite ?"** paragraph proposing the natural next layer: security, maintainability, monitoring, documentation, or UX. Keep it to 2–4 bullet points maximum. The user decides whether to act on any of them — the goal is to surface what a senior engineer would think of next, not to impose extra work.

### Git conventions
- **Always push to `main`** — all commits go directly to the `main` branch.
- Commits: brief English messages describing what changed.
- Main branch: `main`
- **NEVER put a `Claude-Session:` URL in a commit message.** The default
  convention appends one; on this repo it must be dropped. It is a link into a
  private tooling session published in the history of a PUBLIC repository, it
  is useless to every reader of that history, and it cannot be taken back once
  pushed — a rewrite leaves the old commit reachable by SHA. `Co-Authored-By`
  stays; it names an author, which is what a trailer is for. Set by the user,
  standing: *« enlève l'url et ne remets jamais ceci — pas utile »*.
- **ALWAYS CHECK THAT THE PREVIOUS DEPLOY HAS FINISHED BEFORE PUSHING TO `main`.**
  `deploy.yml` carries `concurrency: { group: pages, cancel-in-progress: true }`,
  so a second push while the first is still deploying does not queue behind it —
  it **kills** it. The build that was in flight never reaches the users, and
  nothing says so afterwards: the commit is on `main`, the workflow list shows a
  grey *cancelled* that reads like a hiccup, and the site keeps serving the
  version before it. Query the run for the previous SHA and wait for
  `completed`; push the feature branch first if you need somewhere to put the
  work meanwhile. **Set by the user, standing** — and recorded here because it
  was broken twice in one session: once by me on the reasoning that a
  documentation-only push was harmless (it is not — what matters is not what the
  new push contains but what the cancellation destroys), and once by two runs
  created for the same SHA in the same second. A rule that lives only in a
  conversation dies with it, which is the whole reason this line exists.

## Key Conventions for AI Assistants

1. **Multi-file architecture** — Code is organized across `src/views/curator/` (17 `*View.tsx` + 16 modals/overlays), `src/hooks/` (24 hooks), `src/utils/` (`lotUtils`, `imgCache`, `lotInvariants`, `diagnostic`, `cryptoBackup`, `oauthDiag`, `oauthReturn`, `stats`, `gdriveApi`, `cloudProvider`, `dropboxAuthCore`, `rotation`, `suggest`, `watchlist`, `geo`, `tobaccoDb`, `docPage`), `src/components/Charts.jsx`, and `src/components/curator/` (icons, primitives, FormFields, Modal, BottomDock, AICard). `App.tsx` is the state + hooks owner and renders `<CuratorApp />`; it delegates all business logic to hooks. Do not add code to App.tsx that belongs in a hook.
2. **TypeScript strict mode** — `tsconfig.json` has `"strict": true`. All new code must be type-safe. Use `any` sparingly and only for genuinely dynamic values (context, external APIs, schema migrations on imported data).
3. **Build tools** — Vite + npm. Run `npm run dev` to develop, `npm run build` to produce `dist/`. No CDN dependencies in source; all imports go through npm.
4. **READ THE EXIT CODE OF EVERY GATE — never a piped summary.** This rule already existed for vitest (« a run can be GREEN and still exit 1 ») and the general form was learned the hard way: build 46 was pushed with a commit message asserting « Gates: typecheck, … » while `tsc` was **failing on four `TS18047` errors in a test file added after the last typecheck run**. Two mistakes compounded. (a) A gate was run BEFORE the last file was written and not re-run — the sweep must come after the final edit, always. (b) The habit of `npx tsc --noEmit 2>&1 | head -3; echo TSC_OK` and `npx knip 2>&1 | tail -1` **discards the exit code**: a pipeline reports the status of its LAST command, so `head`/`tail` returns 0 whatever the gate did, and `echo OK` then prints unconditionally. That is how a red gate read as green locally and the deploy died on `main`. It also sent the first diagnosis to the wrong gate entirely (knip, whose step merely ran after the failure). Run each gate bare, or redirect to a file and echo `$?` — `set -o pipefail` if a pipe is unavoidable. **A claim about a gate is only true if its exit code was seen.**

5. **ESLint** — Run `npm run lint` before committing. **Zero errors required.** **Read the whole summary, not `| tail -1`** — that truncation is how two releases shipped a `no-undef` and had their DEPLOY blocked by the gate (which is the gate working; missing it locally was not). `npx eslint . | grep -cE "  error  "` answers the only question that matters.

   **The warning budget: 7, all `react-hooks/exhaustive-deps`, all deliberate.** It was 20, then 9. Nine were **dead `eslint-disable` directives** — a suppression that no longer suppresses anything is worse than none, because the next edit to that hook gets its real dep problem silently swallowed; they were read one at a time and removed. **Do NOT run `eslint --fix` on them**: one of the nine (`useAppUpdate.ts`) was not dead but MISPLACED — `disable-next-line` sat above a comment block instead of the dep array 15 lines below, so it disabled a comment while the warning it was written for stayed live, showing up as two unrelated notes at opposite ends of the file. `--fix` would have deleted it and left the warning. Moving it removed two warnings at once.

   **Two more went when the LOT modal was taught to report itself.** `PipesDetailView`'s twin effect had been written `[!!maintForm, setMaintFormOpen]` and drew TWO warnings at once — a missing dep and "a complex expression in the dependency array" — and copying that shape for the lot modal would have made it four. Hoisting the boolean to a named `const` above the effect satisfies the rule exactly (the dep becomes statically checkable) while keeping the behaviour the inline `!!` was there for: fire on OPEN/CLOSE, never on a keystroke inside the modal. **When an effect keys on "is this modal open", name the boolean** — the inline coercion buys nothing and costs two warnings.

   **The remaining 7 are judgements and must stay warnings.** Each is a dep deliberately omitted (`Modal`, `useSessionStore`, `useStartupNotice`, `useStorageQuotaWarning`, `DocPageView`, `InventoryListView`, `PipesListView`). Adding what the rule asks for is exactly the change this file documents as the **prefill-race trap** — an effect that writes a user-editable field must NOT list that field, or clearing it to type re-fires the effect and snaps the value back, and the user reports "I can't change this field". Blanket-fixing them trades a clean count for real bugs.
6. **Test suite** — `npm test` runs ~5885 tests across 305 source test files with Vitest (re-measured; `doc:check` warns when they drift past ±20 % cases / ±10 % files). **A run can be GREEN and still exit 1** — see `src/__tests__/drainScheduler.ts` for the one way that happens and the hook that closes it; read the exit code, not the summary (incl. fast-check property tests on lot lifecycle). All tests must pass before committing. Add tests for new view components using `renderWithCtx()` from `src/__tests__/viewTestUtils.tsx`. Automated a11y smoke tests run via `jest-axe` in `src/__tests__/a11y.curator.test.tsx` — they catch missing labels, removed focus rings, missing modal ARIA, etc.
7. **Inline styles** — The project uses CSS-in-JS (inline `style` props). Do not add CSS files or CSS-in-JS libraries. Colors come from `src/theme-curator.ts` via the `C.*` tokens; fonts from `F.*`. Never reach for hardcoded hex values in views.
8. **French language** — UI strings, labels, and AI prompts are in French. Keep new UI text in French. Add each key to EVERY dictionary in `src/i18n/` (`fr,en,es,de,it,pt` today — aggregated as `LANG` by `src/i18n.ts`); `doc:check` AUTO-DISCOVERS them and enforces parity against `fr`, so fr+en only fails CI.

Bump `cave-tabac-vXXX` in `public/sw.js` **ONLY** when icons (`*.png`) change, or when SW logic in `sw.js` itself changes — **not** for `manifest.json` (see the CACHE_NAME section: `doUpdate()`'s unconditional purge delivers it without an SW churn). **NEVER bump `sw.js` for `src/` or `.html` file changes.**

"jar" : "cellar"`) — **Round-15 lifecycle MED-1: the SAME rule as the weightG>0 branch, NOT `!!dateOpened`. A legacy finished lot that migrateData stamped `originalStatus:"jar"` (finished with no dateOpened) used to land in `status:"cellar"`+`originalStatus:"jar"`, an impossible state that trips the `cellar-not-jar-origin` invariant; the two Réactiver branches now agree.** When the target is jar, `dateOpened` defaults to today in the prefill (invariant #4). **Round-15 lifecycle MED-2: `applyLifecycleDates` clears `disposed:false` on the manual JAR branch too (not just cellar) — a jar lot is active and can't be "disposed"; a manual reactivate-to-jar used to leak `disposed:true` onto an active lot.** When `status === "finished"`, the edit form shows a **✓ Consommé / 🚮 Éliminé** toggle (field `disposed`). `disposed: true` excludes the lot from the **Lots finis** counter only; sessions logged against that lot before disposal still count in the monthly consumption chart (they were genuinely smoked at the time). **Auto-revert removed**: `applyLotWeightDelta` used to auto-revert a jar lot to cellar when a positive delta (session edit/delete) brought its weight back to `weightInitial` AND `originalStatus === "cellar"`. When the unit changes, `saveWeightUnit` also converts the two unit-scoped stored weights (`sessDefaultWeight` + `watchLowWeight`). **Round-15 HIGH: that conversion goes through the pure `convertWeightUnit(raw, fromUnit, toUnit)` (utils.ts) — do NOT reintroduce an inline `parseFloat(x) || N` + 1-dp-oz version.** The old inline code corrupted small values: a `|| N` fallback replaced a legit small/zero value, and 1-dp oz rounding collapsed anything < 1.4 g to `"0"`, so a 1 g default became **85 g** and a 1 g low-stock threshold became **1418 g** on a g→oz→g round-trip. `convertWeightUnit` returns `null` (leave the stored value UNTOUCHED) for empty/garbage/no-op — never substitutes a fallback — rounds oz to **3 dp** and accepts a comma decimal. Locked by `convertWeightUnit.test.ts`. **The oz precision has been raised TWICE, for the same reason each time, and only the second raise makes the round trip the IDENTITY.** At 1 dp came the corruption above; at 2 dp nothing exploded, but the grid stayed COARSER than the gram side — MEASURED over the 2000 one-decimal gram values from 0.1 to 200.0, **1295 did not survive g→oz→g**, drifting by up to 0.10 g, and 0.1 g still went to `"0.00"` and back to `"0"`, which greys the session form's Save for ever with nothing on screen saying why. Neither sits on the DEDUCTION grid (`roundWeightToUnit`, 1 dp g / 2 dp oz) — the default is a prefill re-rounded at save, the threshold is only ever compared — so the third decimal never puts an unrepresentable weight near a lot. **RESIDUAL, disclosed:** oz→g→oz still drifts one gram-grid step (0.1 oz is 2.835 g, stored `"2.8"`, read back 0.099 oz), because the GRAM side stays at 1 dp — the grid the whole app deducts on, which is not this function's to move. g→oz→g is the direction a preference actually travels. 26. **Web requests — SEARCH, do not crawl. Binding on this assistant and on
    every agent it spawns.**
    - **Reach for `WebSearch` first, always.** A search result is served by an
      engine that publishers have opted into; it answers most questions from the
      snippet alone.
    - **`WebFetch` only when a snippet is genuinely ambiguous, and only on a host
      that welcomes it.** Respect `robots.txt`. Many sites — retailers and
      review sites in particular — disallow crawlers, and a 403 from one of them
      is that policy speaking.
    - **A refusal is an answer, never an obstacle.** If a fetch is refused
      (`robots.txt`, 403, a bot wall, or the agent proxy), report the blocked
      host and work from the search result instead. Never retry it, never route
      around it, never fabricate a different user agent. This is the same rule
      the environment already applies to its own proxy.
    - **Never automate a sweep of a third-party site.** Repeated fetches to
      build a dataset are a crawl whatever the tool is called, and this project
      has no reason to run one.
    - **What this does NOT cover, stated so nobody assumes it does**: the
      internal behaviour of the fetch tool is not something this file can
      enforce or audit. The rule binds which tool is reached for and what
      happens on refusal — that part is a decision, and it is the part that has
      gone wrong before.
    - **The app itself is already compliant by construction** and must stay so:
      the AI auto-fill uses the provider's server-side `web_search` tool, makes
      no direct request to any third-party site, and the CSP `connect-src` does
      not whitelist one. Do not "improve" it into a fetch.
