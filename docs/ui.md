## Curator UI

- **Entry point:** `src/CuratorApp.tsx` — top-level shell rendered unconditionally from `App.tsx` once terms are accepted. Mounts every Curator view (each returns `null` unless `view` matches), the BottomDock, the modal stack (Search / Settings / Lightbox), and Overlays (DelConfirm, save error/warn, update pill, auto-update countdown, just-updated toast, **WelcomeModal**).
- **Layout / scroll model — WINDOW SCROLL (do NOT refactor without a real-device test):** the app uses plain **window/body scrolling**. `index.html` reset is `#root{min-height:100vh}` + **`body{overflow-x:clip}` (NEVER `overflow-x:hidden`: on iOS Safari `hidden` turns `<body>` into a scroll container, so the `position:fixed` dock positions against that box and floats to the middle on scroll of a tall page; `clip` clips identically without a scroll container)** (NO `overflow:hidden` body lock, NO `100dvh` shell). **iOS-PWA floating-dock guardrails (all reverted once by a roll-back, restored + LOCKED by `src/__tests__/iosPwaDockGuard.test.ts` — do NOT undo):** (1) `body{overflow-x:clip}`; (2) shell `width:100%` not `100vw`; (3) the `nav()` pinch-zoom viewport-meta swap in `App.tsx` is skipped when `IS_IOS_STANDALONE` (mutating the viewport meta recomputes the visual viewport and dislodges the fixed dock); **(4) THE decisive one — `BottomDock` is PORTALED to `document.body` via `createPortal` in `CuratorApp`. A `position:fixed` dock trapped inside the app column drops into flow the instant ANY ancestor gains a containing-block property (`transform`/`filter`/`backdrop-filter`/`contain`/`will-change`) — which the recessed-tone surfaces + the dock's own blurred pill introduce — floating it mid-page ONLY in the installed iOS PWA (Safari-browser masks it). Portaling under `<body>` makes it immune to any ancestor. NEVER un-portal it.** The test asserts these four source invariants so a future revert fails CI instead of shipping "le menu du bas qui flotte" to the installed PWA. The shell (`CuratorApp.tsx`) is `width:100%; min-height:100vh` (**`width:100%`, NEVER `100vw`** — 100vw ignores the scrollbar and overflows horizontally, which floats the fixed dock on iOS PWA) centring a `maxWidth:760` `position:relative` column (raised from 600 to 760, so iPad / large screens use more horizontal width — a strict no-op below 600px, so phones are unaffected) that grows with its content; the page scrolls the window. The `BottomDock` is `position:fixed; left:0;right:0; bottom:0` and its inner pill caps at `maxWidth:736` (= 760 column − 12×2 margin — bump this in lock-step with the column cap so the centred pill stays aligned) with `padding-bottom: max(calc(env(safe-area-inset-bottom,0px)-20px),6px)` ("au ras + compact" — was `-12px`/floor 12px; the floating pill now dips ~20px into the home-indicator safe area, leaving ~14px clearance so it stays just above the indicator bar, floored at 6px for env=0 devices). The pill is also thinner (padding `5px 4px`, radius 20) and the tabs shorter (minHeight 42, icon 17, label fs(9)). **The five `top: 0` banners now RESERVE their height, like the tasting banner always has.** The shell has carried `paddingTop: bannerH` for `CuratorTastingBanner` for a long time, with the reason written on it — *"Keeps the active view's TopBar icons tappable during a live tasting"* — and the five banners in `TOP_BANNER_ORDER` never got the same treatment. They are `position: fixed; top: 0` at z489-492 against the TopBar's `sticky` z20, so at the top of a page a banner covered it **outright**: measured at 390 px in a device harness, the export reminder is **110 px tall and hides all 65 px of the TopBar**, every one of its four buttons (search, trash, settings, +) with it. **The mechanism is deliberately the existing one, not a new one**: each banner root carries `data-top-banner`, a single `TopBannerHeightProbe` in `CuratorOverlays` measures whichever is mounted (`pickTopBanner` guarantees at most one) with a `ResizeObserver` keyed on `pickTopBanner`, and reports up exactly like `onHeight`. The height is MEASURED, never assumed — it varies with the text, the width, the safe-area inset and the user's font-scale setting. The shell **sums** `topBannerH + bannerH` rather than maxing them, because the two STACK: `CuratorTastingBanner` takes the measured height as a `topInset` and sits below whichever top banner is up, instead of painting over it at z2001. Same build **dropped that banner's stale `autoUpdateCountdown ? 44 : 0` term** — the countdown had turned from a ~15 px strip at `top: 0` into a centred `Modal`, so those 44 px had been holding space for something that no longer existed. **A test had been pinning that 44 px for twenty-two releases** and went red on the removal, which is the moment to check who is right rather than which is easier to change: `CuratorAutoUpdateBanner` demonstrably renders a `Modal` (maxWidth 380, own backdrop), so the test was locking obsolete behaviour. Its block in `TastingBanner.test.tsx` now records the reversal and asserts the opposite — that the countdown must NOT move the banner — so restoring the old term turns it red. **Validated on the INSTALLED iOS PWA before shipping** (a purpose-built harness reproducing the geometry; the user confirmed no layout jump and no scroll shift) — the rule this section states for every fixed-positioning change, honoured rather than quoted. Locked by `topBannerInset.test.tsx`, whose own first version read its explanatory COMMENTS as data and reported a phantom sixth banner: it blanks comments before every source assertion now, the same lesson doc:check's gate 15 recorded. **When you add a banner to `TOP_BANNER_ORDER`, give its root `data-top-banner`** — the test fails otherwise, because a banner the probe cannot see goes straight back to covering the TopBar.

**Any change to these values must be validated on the INSTALLED iOS PWA** — the safe-area clearance is exactly what headless can't reproduce. **A FIFTH failure mode, distinct from the four guardrails: the dock DRIFTS mid-screen while scrolling and settles at the bottom when the gesture ends.** Reported with a scrolling screenshot showing the pill halfway up the page, which reads exactly like the in-flow bug and is not it. **The triage is what separates them, and it is one question**: at REST, at the very bottom of a page, is the pill correctly ON TOP of the last content? If yes, `position: fixed` is resolving against the viewport and the four guardrails are irrelevant — verified here in a real render (dock is a direct child of `<body>`, `position: fixed`, `bottom: 0`, and ZERO containing-block-creating ancestors), plus no horizontal overflow at 360 px with twelve overdue pipes (`scrollWidth` 360 = `clientWidth` 360). What remains is the WebKit behaviour where a fixed element painted on the main thread lags behind compositor-driven scrolling. `transform: translateZ(0)` on the outer fixed strip promotes it to its own layer and fixes it — CONFIRMED on the installed PWA. **It does NOT contradict the rule above**: that rule is about an ANCESTOR gaining a containing-block property; this sits on the fixed element ITSELF, which cannot change its own containing block. **A page-height TRIGGER was proposed here and is now FALSIFIED — kept as a correction rather than deleted.** It read *"the trigger was page height, not a code defect"*, on the grounds that the Home's maintenance section had gone from five rows to every overdue pipe (2903 px at 360 px/"L" with twelve) and that this section already says the float appears "on scroll of a tall page". The drift came back on a build whose maintenance section is **capped at five again** — a SHORTER Home than the one that carried the original report — so page height is not what produces it. What survives from that paragraph is only the negative half, and it still holds: the commits blamed at the time touched no CSS and no positioning, and the dock itself is unchanged since the first public commit; do not go looking for a regression in them. **WHAT ACTUALLY CLEARED IT IS NOT SETTLED, and the first answer written here was WRONG — recorded rather than deleted, because the mistake is instructive.** The build carrying `translateZ(0)` was reported as STILL drifting, then as fixed « après avoir fermé complètement l'app ». It was written up as a delivery lesson — a PWA resumed from the app switcher does not reload, so it must have been running the previous build — and the user corrected it flatly: **they were already on the new build before closing.** So the property alone did not clear it; destroying and recreating the web view did. That leaves two readings this file cannot choose between: either the promotion is the fix and a long-lived WKWebView had to be recycled before it took hold, or the recycling alone is the fix and the property is inert. **They are distinguishable only by TIME — if the drift never returns across many launches, the first; if it comes back with no code change, the second** — so do not restate either as established. **The drift DID come back, and the record now favours the promotion.** The prediction assumed the property was IN PLACE and it was not — the wholesale revert to build 18 removed it as collateral. Tabulated: build 23 property PRESENT, drift reported then gone after a full quit; builds 24-30 property ABSENT, drift returned at 30; build 31 property PRESENT, no drift. Twice absent → drift, twice present → none, which is the first coherent correlation this bug has produced. **It is still not proof, and the confound is nameable**: both clean observations had the property AND a freshly recreated web view. Exactly one situation separates them — an IN-PLACE update, where `doUpdate` calls `location.reload()` and WebKit keeps the same web view, unlike a full quit which destroys it; if the drift stays away through a session updated in place, the property is doing the work. **A third explanation was proposed and FALSIFIED in between, recorded so nobody proposes it a fourth time**: that closing the app never fixes anything and merely DELIVERS a newer build, HTML being network-first while a resumed PWA does not reload. It fits the 23 and 30 reports and cannot explain a drift present from the first scroll of a session, which is what was reported. Retired. The plausible mechanism for the second is documented one entry over, at `main.jsx`: mutating `document.documentElement` in the installed PWA recomputes the fixed-position layer and floats the dock, and a reload (which `doUpdate` performs) keeps the same web view while a full quit does not. **The lesson that DOES survive: an explanation that fits the facts is not the same as the one that produced them, and 'the user must have been on the old build' is the shape of guess to distrust — it explains a report by assuming the reporter was mistaken.** The one risk it shipped with is CLEARED: the pill's `backdrop-filter` still blurs under the transformed ancestor (checked on the installed PWA), so WebKit does not treat this transform as a backdrop root and a compositing promotion on an outer strip is compatible with a backdrop-filter inside it — worth knowing before reaching for the same trick elsewhere. **Why window-scroll and NOT an app-shell (hard-won):** an earlier attempt tried a locked-body inner-scroll "app-shell" (`html,body{overflow:hidden}` + `position:fixed` shell + inner `overflow-y:auto` container) to stop a reported floating-dock bug. It DID stop the float, BUT a locked body under `viewport-fit=cover` shrinks the iOS *visual viewport* to the safe-area box, so the shell + dock stopped ~0.5cm above the physical bottom (a background strip showed below the app), and no `bottom:calc(-1*env(...))` overhang reliably pushed them back to the true edge on the device. The layout was **reverted to window-scroll**, which the user confirmed reaches the true physical bottom AND does not float in the installed PWA (the original day-of-changes float turned out to be unrelated to the scroll model — it was gone once the layout returned to the pre-refactor shape). Keep it window-scroll: no body `overflow:hidden`, no `position:fixed` shell, no inner-scroll container, no `src/utils/scroller.ts` singleton (removed — scroll snapshots read `window.scrollY` / `window.scrollTo` again). **CRITICAL: neither Chromium (headless or not) nor Safari-browser reproduces the iOS-standalone `position:fixed` / safe-area / body-lock behaviour — the ONLY trustworthy test for any bottom-dock / fixed-positioning / `100vh|100dvh` / `overflow:hidden`-on-body / safe-area change is the INSTALLED iOS PWA (Add-to-Home-Screen), on a page taller than the viewport so it actually scrolls.** Don't ship such a change on a headless "looks fine" alone. (The confirmed-good window-scroll layout is also tagged at the git "test" release = commit a2423fc, an instant fallback.)
- **Routing:** views route on a `view` string state. No URL change. View keys: `home`, `inv`, `pipes`, `addT`, `editT`, `addP`, `editP`, `addA`, `editA`, `addJ`, `editJ`, `journal`, `acc`, `stats`, `tasting`. The `WishFormView` is gated by `showWishForm || editWishId` (not by view).
- **Design tokens:** `src/theme-curator.ts` exports `C` (palette: brass / oxblood / sage / amber / ember / ivory / cream), `F` (Newsreader display, DM Sans body, IBM Plex Mono mono), `DOCK_ACCENT` per section, `CURATOR_CHART_COLORS`, `catColor(cat)` (which reads `CAT_COLORS` from `constants.ts` — the themed `CURATOR_CAT_COLORS` was deleted). **Fonts are self-hosted** under `public/fonts/` (see Font hosting section below); `index.html` declares `@font-face` inline against `%BASE_URL%fonts/*.woff2`. CSP enforces `font-src 'self'` only — `fonts.googleapis.com` / `fonts.gstatic.com` are no longer whitelisted.
- **Page gutter = 12px (unified at 16, then moved to 12).** Every full-page content block shares ONE horizontal gutter of **12px**: `TopBar`, `PageTitle`, `SectionHead`, the `ZoneHead`/masthead rows, every list sub-title / filter / card-list wrapper, and every detail-view section + hero wrapper. Four coexisting values (14 / 16 / 18 / 22px) were unified down to 16; **the whole gutter then moved 16 → 12 so the tiles align edge-to-edge with the bottom dock pill** (the pill sits at `margin: 0 12px`, maxWidth 736 = 760 column − 12×2 — the user saw the dock wider than the cards above it). The alignment holds at every width: tiles cap at 760 − 12×2 = 736 = the pill cap. **Keep new full-page wrappers at `0 12px …` / `12px` horizontal, in lock-step with the dock pill margin** — if one ever moves, move the other. The exceptions that intentionally keep **18px** are the MODALS (`SettingsModal`, `TrashModal`, `EncryptionPromptModal`, the Session/Tasting confirm modals) — they're narrower, so 18px reads right there. Card/chip/button INTERNAL padding (e.g. `12px 14px`, `14px 18px`) is not a page gutter and is out of scope.
- **Primitives:** `src/components/curator/primitives.tsx` — animation hooks (`useEnter`, `useWAAPILoop`), `AnimNum`, `Spinner`, `Stars`, `Lbl`, `useReliableTap`, `IconBtn`, `PressCard` (state-driven scale), `TopBar`, `PageTitle`, `SectionHead`, `StatTile`, `SpecRow`, `GrowBarH`, `ScreenWash`, `EmptyState`. **No `@keyframes`, no CSS file, no `className`** — all motion is state-driven CSS transitions or WAAPI.
- **Chrome auto-hide on scroll (`utils/chromeAutoHide.ts` + `hooks/useChromeAutoHide.ts`):** the top bar and the dock slide off screen on a downward scroll and return on ANY upward movement — however small — or after `CHROME_IDLE_REVEAL_MS` of stillness. Always visible within `CHROME_REVEAL_TOP_PX` of the top, and never hidden on a page with less than `CHROME_MIN_OVERFLOW_RATIO` of a viewport to scroll (nothing to gain, and the chrome would only flicker).

  **THE SCOPE IS `shouldShowDock`, NOT A SECOND LIST — and that is the whole lesson of this feature.** Auto-hide applies exactly where the chrome is DISPLAYED: if the bars are there they can step aside, if they are not the question does not arise. That criterion came from the user ("toutes les pages où se trouvent les menus") and it is better than the one I started with. It covers the six root views, the catalogue, and the fiches — which are not views at all but sub-states (`detail`/`pipeDet`/`accDet`) rendered under `inv`/`pipes`/`acc`, so they are carried by their list with no extra clause. It excludes the tasting, the eight full-screen forms, the four doc pages and the wishlist overlay, all for one reason: the dock is not there.

  **A HAND-WRITTEN `AUTO_HIDE_VIEWS` PRODUCED THREE PHANTOM STRINGS IN THREE COMMITS, and deriving the decision deleted the class.** `"catalogue"` (the view is `catalog`), then `"detail"`, `"pipeDet"`, `"accDet"` — the last of which SHIPPED the very defect the scope existed to prevent, hiding the fiche's back button. A copied list of ids always agrees with itself and never with the app. There is no id left to write, so none left to invent. `chromeAutoHide.test.ts` asserts the two decisions agree over every id the views declare, and that the shell hands BOTH functions the same gate — a derived rule is still defeated by two different gates at the call site.

  **My original objection to hiding the fiches was weaker than I stated:** their top bar carries the back button, but that is not the only exit (`useBackNavigation` wires system back, `decideBack` closes a drill), and it is never gone for more than half a second since any upward move AND stillness bring it back.

  **A TRANSLATION, never a removal from flow** — the element keeps its space, so content does not jump a pixel under a moving finger. The TopBar is a primitive shared by every view, so it cannot decide for itself: the shell sets a `--chrome-shift` custom property it merely honours, `none` wherever auto-hide does not apply. **`HomeViewV2` does not use that primitive** — it builds its own sticky header on the same recipe, a SECOND call site that had to be wired by hand and is guarded as such. The dock is PORTALED to `document.body`, so it cannot inherit the property and takes a `hidden` prop.

  **`will-change` IS DELIBERATELY ABSENT FROM BOTH.** On the dock it was redundant — the `translateZ(0)` above already promotes that strip, deliberately. On the TopBar it was a PERMANENT layer promotion on an already-blurred sticky element, the kind of chrome this repo has documented iOS rendering drift on; and `will-change` is itself one of the containing-block properties listed in guardrail (4). Do not put them back.

  **Why guardrail (4) still holds:** the dock is portaled under `<body>`, so neither the shell nor the TopBar is its ancestor. The TopBar has ALWAYS carried `backdrop-filter` — itself a containing-block property — so it was already one; the added `transform` changes nothing in kind, and nothing `position: fixed` lives in its subtree.

  `usePrefersReducedMotion` drives the transition to `0ms`: the chrome still hides and returns, it just snaps. **This is the ONLY animation in the app that honours the preference** — the seven others are few-pixel micro-moves on a pressed button, this is a full-width band. Generalising it is separate work, not done.

- **SettingsTabs:** the Settings modal is split into 4 tabs — `data` (Drive + Export/Import + AI), `prefs` (units, language, sections), `app` (install + update + diagnostic), `help` (links). - **Lightbox ghost-click defense:** `src/views/curator/LightboxOverlay.tsx` uses a `closingRef` ref-based lock (NOT state — React batching can let a second close call through before the state has propagated) plus a deferred `setLightbox(null)` 260ms after the fade-out. Without this, the ~150ms ghost-click iOS/Android emit on long-press → tap landed on the trash icon underneath the lightbox X button, silently deleting the underlying object. The lightbox tests use `vi.useFakeTimers()` + `vi.advanceTimersByTime(300)` to assert the deferred close. Do not collapse the deferral to a synchronous `setLightbox(null)` — the regression test will pass even though the bug returns.
- **Modal ghost-click defense:** `src/components/curator/Modal.tsx` carries an internal `shouldRender` state. When `open` flips false the modal flips `mounted` to false instantly (so the opacity + transform transition plays) but defers the actual unmount by ~320 ms via `setTimeout`. Same mechanism as the lightbox but generalized to every `Modal` (Settings, Search, LotForm, GdriveConfirm, Encryption prompt…). The motivating case was closing Settings via its X — the synthetic ~150-300 ms click landed on HomeView's search icon directly underneath and opened the search modal. The `useDeferredFalse(value, delay)` hook in `CuratorApp.tsx` extends the same defence to the lazy-loaded `SettingsModal` and `TrashModal` mount gates (`importModal`, `trashOpen`) so the lazy chunk stays mounted during the defer window. If you add a new modal that opens from a tappable surface that overlaps another tappable surface, follow this pattern.
- **Curator-specific ESLint config:** `eslint.config.js` has a `src/(views|components|hooks|__tests__|CuratorApp.tsx|theme-curator.ts)/curator/**` block that disables `no-unused-vars`, `no-unused-expressions`, `react-hooks/rules-of-hooks`, `react-hooks/set-state-in-effect`, `prefer-const`, `no-empty` for the vendored bundle.
- **Hook-order trap:** Curator views must call **all hooks before any early return**. Any `if (view !== "...") return null;` must come AFTER every `useMemo`/`useEffect`/`useEnter` in the component. Putting the early return first triggers "Rendered more hooks than during the previous render" when the view becomes active.
- **Prefill-race trap (invariant):** a `useEffect` that writes to a user-editable text field via `setForm` / `setTasting…` / `tastingSetupUpdate` / equivalent **MUST NOT list that same field in its dependency array**. The legitimate triggers for an on-mount prefill are screen-entry signals (`view`, `tasting?.stage`, `open`) and global toggles (`accountingEnabled`, language), never the value the effect writes back. Listing `form?.weightG` (or any other text input) makes the effect re-run on every keystroke: clearing the field to type a new value (backspace → `""`) re-fires the effect, which sees an empty value and immediately re-fills with the default, racing against the user's next keystroke and silently snapping the input back. The user-facing symptom is "I can't change this field". When you need a guarded reset of a value (e.g. clearing a stale filter whose target option disappeared, like `JournalView.tsx:118-122` or `PipesListView.tsx:61-65`), that's safe **only** because the reset is gated on the value being missing from a derived list — the steady-state branch is a no-op, so user input doesn't trigger the setter. Audit any new `useEffect` whose body writes to `form.X` / `tasting.X` against the rule: the field must come out of the dep array, or the effect must be guarded so it's a strict no-op in normal user flow.
- **Welcome popup:** `src/views/curator/WelcomeModal.tsx` — shown once per user (gated by `localStorage["cave-curator-welcomed"]`). Mounted inside `CuratorApp` so it only appears after the terms gate. Briefly introduces the app and reminds the user about local-first storage + optional Drive backup. Single "C'est noté" / "Got it" dismiss button.

Semantic tokens (`C.good` / `C.warn` / `C.bad`) were removed: views reach for `C.sage` (success), `C.amber` (warn) and `C.oxbloodHi` (error) directly so the surfaces compose with the same hue family as the section accents.

**No hardcoded hex in the Curator UI.** Every colour must come from a `C.*` token — a scoped ESLint rule (`no-restricted-syntax` in `eslint.config.js`, on the Curator source: `CuratorApp.tsx` + `components/curator` + `views/curator`) **errors** on any hex literal, both standalone (`background: "#2a1816"`) and inside template literals (`radial-gradient(…, #2a1612, …)`). The six one-off decorative tints that used to be raw hex were consolidated into `C.*`: `panelWarn` (error/warn callout panel), `washEmber` / `washMoss` (warm/cool radial-gradient focals), `docBadgeCave` / `docBadgePot` / `docBadgeFin` (help-doc status-badge backgrounds). `theme-curator.ts` itself is exempt (it DEFINES the tokens); `EB.tsx` is deliberately theme-independent (the theme could be what crashed) and lives outside the curator scope. The same rule block also bans raw `fontSize: <literal>` (every size must flow through `fs()`/`fsInput()`).

**The hex rule had a blind spot: `rgba()` / `hsl()`.** The hex selectors never looked at functional colour notation, which is exactly how `BottomDock`'s frosted pill shipped as a raw `rgba(18,24,21,0.24)` — a dark glass that stayed dark in light mode, leaving the gold dock labels at 2.27:1. Only `npm run theme:contrast` caught it, and only because it renders; nothing static could see it. Four new selectors now cover `rgb()`/`rgba()`/`hsl()`/`hsla()` in both `Literal` and `TemplateElement`. **The rgba ban is deliberately TINTED-ONLY** (a negative-lookahead regex exempting `rgba(0,0,0,α)` and `rgba(255,255,255,α)`): a pure-neutral value is a scrim or a drop shadow and reads the same in both modes, so banning those would have forced ~24 pointless conversions — and an over-strict rule gets correct code rewritten to please it. A NON-neutral rgba is always a palette decision, and it can only be right in the one mode it was eyeballed in. It flagged exactly **2** sites on its first run, both real: `C.oxblood` written out longhand as `rgba(168, 69, 63, 0.08)` in `SettingsModal` **one line above a border that already used `alpha(C.oxblood, …)`** (so the border followed the mode and the background didn't), and a green-tinted near-black modal scrim. `hsl()` is banned outright — it has no neutral idiom here and had zero sites. Probed in both directions, including the historical dock-pill value. **Note the scrim decision**: `Modal.tsx`'s backdrop was NEUTRALISED to `rgba(0,0,0,0.78)`, not tokenised — `alpha(C.bg, …)` would be wrong, because in light mode `C.bg` is cream and the backdrop would wash the page out instead of dimming it. A scrim's job is mode-independent; use a neutral, not a token.

**Colour themes.** The `brass`/`brassHi`/`brassDim` tokens are CSS vars with the classic hex as fallback (`var(--c-brass, #d4a661)`), so the "gold" primary identity is swappable at runtime: `THEMES` (theme-curator.ts) maps each theme id to the `--c-brass*` overrides, `applyTheme(id)` writes them onto `<html>` (seeded pre-mount in `main.jsx`, re-applied on change by App.tsx's `themeId`/`saveThemeId` via `cave-theme`), and every derived palette (DOCK_ACCENT, CARD_ACCENTS, CURATOR_CHART_COLORS) holds the var() string so it follows the swap — NO React re-render (same mechanism as `--cave-font-scale`). Ships `brass` (default) + `steel` (bleu acier) + `english` (anglais — a British forest-green vault). Themed tokens: the brass accent trio, the surface family (`bg`/`bg2`/`bg3`/`card`/`cardHi`/`rule`/`rule2`), AND `title` (the large serif display titles: Home masthead + "Bibliothèque" + the emphasised word in every page title) — all var-with-fallback. `steel` swaps the whole atmosphere + depth (warm green-black vault → cool blue-slate), not just the accent. **`C.title` is separate from the accent on purpose**: the pale steel-blue accent read washed-out as a huge title, so `steel` points `--c-title` at a crisp near-white (`#dbe6f2`) while `english` uses a bright leaf-green and `brass` falls back to the gold. Use `C.title` (not `C.brass`) for any new large display title. **Light/dark mode**: a second axis (`cave-theme-mode`) orthogonal to the colour theme — EVERY colour token (surfaces, text, semantics oxblood/sage/amber/ember/steel, ink, the decorative washes) is now `var(--c-*, <dark fallback>)`. `MODE_LIGHT` (theme-curator.ts) is the shared parchment palette (cream surfaces + dark text + darkened-for-AA semantics); `applyTheme(themeId, mode)` writes `MODE_LIGHT` + `THEMES[id].lightAccent` (a DARK accent, legible on cream) in light mode, or `THEMES[id].vars` in dark. All light values WCAG-AA-validated. `THEME_VARS` lists every var to clear on each apply. **Any new colour MUST be a `C.*` token** (the no-hex rule already enforces this) so it flips with the mode — don't hardcode a light/dark value. Steel surfaces are blue-shifted at matched luminance so every text/border contrast pair carries over (`tx3` on `card` stays ≥ 4.5:1 — validated). Semantic oxblood/sage/amber/ember + the text tokens (tx/ivory/…) intentionally stay so danger/success/warn coding + readability survive the switch. **Translucent tints of a themed token MUST use `alpha(token, "AA")`** (theme-curator.ts) → `color-mix(in srgb, token AA%, transparent)`, NOT the legacy `token + "AA"` / `${token}AA` 8-digit-hex concat — that produces invalid CSS (`var(…)AA`) once the token is a var(); the sweep migrated every brass-family alpha site. **SVG fills/strokes that use a themed token must be set via `style={{fill}}`/`style={{stroke}}`, never the presentation attribute** — WebKit doesn't evaluate `var()` in SVG presentation attributes (Charts.jsx, primitives `Stars`, `Ico`/`Orn` route colour through `style`/`currentColor`). To add a theme: add an entry to `THEMES` + a `theme_<id>` i18n key ×5; to theme MORE tokens, varize them in `C` (var-with-fallback) and add their `--c-*` to the theme's `vars` + `THEME_VARS`. **Verify with `npm run theme:contrast`** — the palette is SIX combinations (3 themes × light/dark) and the app was hand-tuned in exactly one of them (dark brass), so five were never checked by anything. The script renders all six across the shared layout screens (33 of them) and measures every visible text element against its effective background as a WCAG ratio (large text 3:1, the rest 4.5:1), failing below 3:1. It found two real defects on its first run: (1) **the BottomDock's frosted pill was a raw `rgba(18,24,21,0.24)` inline in `BottomDock.tsx`** — a DARK glass that stayed dark in light mode, leaving the gold dock labels at 2.27:1; it is now the `C.dockPill` token with a light-mode value, the dark fallback byte-identical so the installed-PWA look is untouched. (2) the unthemed `CAT_COLORS` split told in full below — **since fixed, and the acceptance the check carried for it was deleted with it.** Two classes are deliberately NOT failures: text over a **gradient** (the backdrop is not one colour, so any ratio would be fiction — the "Ce soir ?" hero and the CTA stay a manual judgement) and text inside a **disabled control** (WCAG 1.4.3 exempts inactive components — the greyed AICard at 0.7 × 0.6 with no API key, and the form submit at 0.5 until the required fields are filled). **That second exemption was narrowed, and this is the load-bearing part**: it used to be reduced opacity ALONE (`alpha < 0.99`), i.e. any dimming claimed the exemption — which quietly reclassified a genuine defect as acceptable. The inventory card's **POT / CAVE badges** wore `opacity: 0.75` as typographic de-emphasis of the word beside its count; that cost ~40% of the contrast (3.68:1 and 3.23:1 in light mode at 11px, vs 6.44:1 / 5.27:1 at full opacity) and the check waved it through as "deliberately dimmed" on the busiest screen in the app. Reduced opacity is not evidence of disablement, so the walk now also looks for an inactive CONTROL (`aria-disabled` / `:disabled` / `cursor: not-allowed`) and grants the exemption only then; the badge opacity was removed. **Never use `opacity` to de-emphasise TEXT** — reach for a dimmer token, so the ratio stays measurable. Verified by probe (re-adding the badge opacity now reports it with NO `[dimmed]` tag). The same pass gave `PressCard` an `ariaDisabled` prop: the convention for disabling one is `onClick={cond ? undefined : cb}`, which drops `role` and `tabIndex`, so AICard's greyed buttons were announced as plain text — a screen-reader user was never told a search button existed. Its sibling, the `FormFields` submit, had carried `aria-disabled` all along. Everything between 3:1 and AA is reported as a warning to triage — **and that triage was done: 313 → 32 warnings, 0 failures, by retuning SEVEN light-mode tokens** (`--c-tx3` #726a52→#67604a, `--c-sage` #367048→#346c45, `--c-sage-hi` #3f7a52→#305d3f, brass `--c-brass` #7d5f18→#7a5c17 + `--c-brass-hi` #8a6a1f→#695018, steel `--c-brass-hi` #356a94→#2c587a, english `--c-brass-hi` #367a4d→#295e3b). Two things made that pass safe rather than a blanket darkening: the values are **computed to clear 4.5:1 against the DARKER of the two light grounds** (the page, not the card), and each is retuned **for its ROLE** — a `*-hi` token is a brighter sibling in dark mode but must go *darker* than its base in light mode, since "hi" means "more emphasis" and on cream emphasis is weight, not luminance; keeping `--c-sage-hi` lighter than `--c-sage` is what left it under AA. The **32 residuals were deliberate at the time**: 30 were `dimmed` (an ancestor `opacity` — WCAG 1.4.3 exempts inactive components) and 2 were dark-mode `tx3` on a journal card at 4.18:1 / 4.29:1 — the `tx3`-on-`card` hair's breadth the palette had always carried. **Those last two were FIXED** by raising `tx3` #8e8773 → #958e7a (4.98:1 on `card`, 4.58 on `cardHi`), so no TEXT anywhere in the app is under AA now; only the `dimmed` class remains. Re-run the check after ANY light-mode token change; a raw `rgba()` inline in a component is the one thing it can't see coming (that was the dock-pill defect).

**The checks had never rendered a fiche or a modal.** `SCREENS` (shared by `i18n:layout` and `theme:contrast`) walked lists, forms and Settings and not one detail page or dialog, in either check, ever. That is not a small gap: **four light-mode semantic tokens were under AA as text with every instance on exactly those surfaces** — `steel-hi` 3.87:1 (the "Collections" label on all three fiches), `ember` 4.22 (accessory brand; the trash kind label at 9px), `amber` 4.27 (trash + shopping status lines), `oxblood-hi` 4.34 (pipe brand, the aging Notice, both modal delete actions) — and the **trash row clipped 84% of the item name in German at the L text size**, a CLIPPED failure by `i18n:layout`'s own rule on the one screen whose purpose is telling you what you are about to delete for ever. Six screens were added (three fiches, the lot modal, trash, shopping) and both checks now pass over 20. Four things are worth keeping: **(1) the seed is a screen GATE, not decoration** — the trash indicator needs a `deletedAt` row, the cart needs a genuinely low-stock rebuy tobacco (`computeShoppingList` requires `0 < activeWeight <= threshold`, so an already-EMPTY tobacco does not qualify, which is what made the shopping screen unreachable at first), TagChipRow needs tags; `i18nLayoutHarness.test.ts` now asserts each. **(2) An `expect` marker must be exclusive to its screen.** `modal-lot` used `lbl_initial`, which the fiche can also render, so the layout run reported the screen as reached while measuring the fiche underneath — and the contrast run, at a different width, called it unreachable. Two checks disagreeing about one screen is what exposed the marker; it is now `lbl_current`, verified unconditional and modal-only. **(3) A modal opened from a card needs KEYBOARD activation.** The card tap fires through `PressCard`'s pointer path, which installs a one-shot capture listener to swallow the trusted click that follows (the ghost-click defence) — so a programmatic click on the lot row was eaten and the modal never opened. `focus()` + Enter goes through the row's `onKeyDown`, and exercises the a11y path as a bonus. **(4) Fixture STRING LENGTHS are load-bearing, and a real export settled them.** A 41-char blend name was tried and turned the run red in five places that are all by-design ellipsis (Home suggestion rows, the shopping row) — encoding that as a FAILURE would freeze a design decision as permanent red, the over-strict-guard trap. But the user's own 58-tobacco export contains `633: Virginia Flake with Perique` (32) and `Savinelli Marte Rusticated 320 KS` (33), so "41 is unrealistic" was right and "17 is enough" was not. What the real data DID expose, and the synthetic fixture structurally could not: the Home "Familles" row gives its label 66px after a 6px dot, a 26px bar and a 26px percentage, so **`Aromatique` (71px) and `Virginia/Burley` (88px) were clipped at the DEFAULT text size in French** — six of the fifteen canonical categories, on every user's home screen. Those are enum VALUES, so both are now seeded and the label wraps. The lesson generalises: a fixture built from convenient short strings measures a UI no user has.

**The rest of what the audit had already rendered.** The SIX surfaces that had findings were promoted first; the audit had rendered **24**. "Measured clean once" is not "covered" — nothing stopped the other eighteen from regressing. Nine more are now in, prioritising the FORMS (label + field + hint on every row is where German runs longest, which is why `form-tobacco`/`form-pipe` were added back earlier): the session / accessory / wishlist forms, both EDIT forms, the lot FORM modal (a different component from the lot DETAIL modal already covered — `LotFormModal`, and the one with the dense field grid), the maintenance modal, the journal's session-detail modal, and the tasting setup. **20 → 29 screens (33 later, below); both checks pass** (`theme:contrast`: 3 themes × 2 modes × 29, nothing below 3:1; `i18n:layout`: no clipping in fr@M or de@L/360). Two things this pass added to the method. **Every marker was checked for exclusivity BEFORE use**, against `src/views` + `src/components` — the `lbl_initial` defect made that a rule rather than a habit, and `i18nLayoutHarness.test.ts` now ENFORCES it: a marker shared by two screens fails the suite, with one documented exemption (`lbl_edit`, the edit-mode overline — an edit form is literally the same component as its add form, so no marker can separate them; the navigation path is what distinguishes them, and the test asserts the exemption is actually in use so it can't become dead licence). **The navigation labels are worth grepping, not guessing**: the journal's "+" is `btn_new_session`, not `btn_add` (it pre-fills date + time, so it is its own control) and the wishlist chip is `lbl_wishlist`, not `f_wish` — both wrong on the first attempt, and both surfaced as a LOUD failure (a missing key dies; an unreachable screen fails the run) rather than a silently skipped screen, which is the property that makes this list trustworthy.

**The coverage now equals what was measured.** The last three surfaces the audit had rendered and I had not promoted: the **wishlist LIST** (the inventory in `wish` mode — distinct from the wish FORM), the **catalogue**, and the **global search modal** (whose group headers only render once there are results, so typing a query is part of reaching it — correctly, since an empty search modal is just a text field). ## Accessibility invariants

Hand-audited and locked by `src/__tests__/a11y.curator.test.tsx` (jest-axe smoke test on every top-level Curator view, WCAG 2.1 A/AA ruleset, fails CI on any serious/critical violation).

- **Focus indicators**: every `<input>` / `<textarea>` / `<select>` that calls `outline: "none"` MUST pair with `useFocusRing()` (`src/components/curator/FormFields.tsx`) — the hook applies a 2px brass `boxShadow` on focus. Never reintroduce a bare `outline: "none"` without a replacement. `PressCard` carries its own focus ring via local state.
- **Form labels**: `TextField` / `TextAreaField` / `SelectField` (FormFields) generate `useId()` and pass `htmlFor` to a real `<label>`. Standalone inputs in views (SearchModal, SessionFormView tasting-notes textarea, TastingView weight/notes, SettingsModal sessDefaultWeight + ApiKeyInput) MUST set an `aria-label`.
- **Touch targets.** **The two standards, because 44 gets quoted without its source**: WCAG **2.2 SC 2.5.8 "Target Size (Minimum)" is 24 × 24 and level AA** — the bar normally required; WCAG 2.1 SC 2.5.5 "Enhanced" is 44 × 44 and level **AAA**, which is also Apple's HIG figure. **This project adopted 44 as a house invariant**, stricter than compliance demands — so a sub-44 element is not automatically a defect, and a measurement against 44 needs saying so. `IconBtn` default `size = 44`. `ActiveFilterPill` clear button = 28 minimum. `ApiKeyInput` reveal/save/clear buttons = 36 minimum. Never drop these below the documented minima.
- **The 12 filter/sort `<select>`s, which failed even AA.** Measured across five screens at 390 px: they were **18–20 px tall inside a 36 px wrapper** that carried the border and the background. So the control LOOKED 36 px and only its middle third opened the list — `elementFromPoint` on the wrapper's padding returns the `<div>`, which has no handler. **That is worse than a small control**: a small one you aim at, one that looks twice its size you miss without understanding why. (`appearance: "none"` also disqualifies them from SC 2.5.8's "user agent control" exception — the author modified the presentation.) The fix moves the wrapper's vertical padding onto the select (`alignSelf: "stretch"` + `minHeight: 44` on the wrapper, `padding: "0 …"`), so the whole visible box is live: **42 px, top/middle/bottom all hitting the select**, verified with `elementFromPoint`. Four views: Pipes / Acc / Inventory / Journal.

A flex item defaults to `min-width: auto`, so the sort wrapper beside them refused to yield the 8 px; it now carries `minWidth: 0`. **Trading a 2 px accessibility shortfall for a horizontal overflow is a bad trade** — measure the row after any change here. Locked by `tapTargets.test.ts`, whose own first version was satisfied by the fix's explanatory COMMENT and so stayed green under probe; it blanks comments now, the third time that trap has been hit.

It now also fails on **any element that can be dragged sideways**: `overflow-x` computed `auto`/`scroll` with `scrollWidth > clientWidth`. **The trap that creates them is `overflow-y: auto` ALONE** — CSS computes the OTHER axis to `auto` as soon as one is not `visible`, so a container that only ever meant to scroll vertically becomes horizontally draggable the moment anything inside it overflows; `SettingsModal`'s body is exactly that. Deliberate scrollers carry **`data-hscroll`** (`ScrollableChipRow`, the Stats calendar) — presence is an ACKNOWLEDGEMENT, not a claim of correctness, the same philosophy as `no-unscoped-lot-read`. **Probed by re-introducing the defect: the gate reproduces the user's report verbatim** (`402px/l/fr/settings-data: slides sideways by 3px`). The strip is a `ScrollableChipRow` and the DOM scroller persists its `scrollLeft` across re-renders — the same fact met on the inventory chips. **Its answer there, `resetScrollSignal` (jump to the far left), is the WRONG answer here**: a tab strip must show whichever tab is active, which is a different target in each direction, and a fresh open on a persisted right-hand tab was equally broken in silence. It reads `offsetLeft`, NOT `getBoundingClientRect`, because the modal opens under a transform transition and a scaled rect would give a scaled delta against an unscaled `scrollLeft`. **THE METHODOLOGICAL FINDING IS WORTH MORE THAN THE FIX: a headless click MASKS this defect.** A Playwright `.click()` dispatches real mouse events, which FOCUS the button, and the browser then scrolls the focused element into view — the same sequence measured 18 px (flush, nothing clipped) instead of the reported clipping. That no-focus path is what an iOS tap on a `<button>` does — the very fact that made `preventScroll` necessary. **When checking whether a scroller lands where it should, activate WITHOUT focus, or you are measuring the browser's focus-scroll rather than the app.** Locked by `chipRowScroll.test.ts` (7 cases incl. idempotency and the do-not-move case) + the wiring block in `SettingsModal.test.tsx`; the arithmetic is unreachable from jsdom, which reports every layout offset as 0, which is why the decision is a pure function.
- **A Settings tab that slid left and right, and the three defaults that mean "do not shrink".** Reported from the app with a screenshot (« dans la page données des settings l'ensemble bouge de gauche à droite. Pas sur les autres »). MEASURED at the reporter's width, 402 px CSS, at the **"L" text size**: the Données tab's content container was a **3 px-wide horizontal scroller** — enough to slide the whole page under a finger, not enough to look like anything but a glitch. At 360 px it was 30 px, and the Préférences tab was affected too. **Three causes, each a CSS default whose meaning is "refuse to shrink":** (1) `Section`'s body is `display: grid` with no `grid-template-columns`, so the implicit track is **`auto`, which cannot go below its content's min-content width** — the "Clé API" row has a min-content of **361 px** (the next widest is 267), so ONE row sized the column and dragged all five rows of the AI section out to 361 px inside a 340 px box; (2) `Row`'s label half had no `minWidth: 0`, and **a flex item defaults to `min-width: auto`** — exactly this was learned on the inventory toggles, same default, one layout mode over; (3) `Segmented` is `inline-flex` with no wrap, so six language options (or the two dated date-format labels) forced the row wider than the panel — and it **cannot shrink instead**, being `overflow: hidden`, so shrinking clips the option labels it exists to display. The `FormFields` submit is a real `<button disabled aria-disabled>` and was already correct — it is the pattern the rest now matches. **The transient-busy sites are deliberately NOT this** (`geoStatus === "loading"` in SessionFormView / TastingView): a momentary in-flight action is `ariaBusy`, not disabled.
- **Semantic headings**: `PageTitle` renders `<h1>`, `SectionHead` and `ModalHeader` render `<h2>`, **`FormSection` renders `<h2>`** (it was `<h3>`; see below). Inline `style` overrides browser defaults (`font-weight: 400`); never replace those with plain `<div>`.
- **The model above has been written here, and FOUR surfaces never used `PageTitle` at all, so they built their own hero out of a `<div>` and inherited none of it.** `HomeViewV2`'s masthead (« Bibliothèque », fs 44) — so the app's LANDING screen had no `h1` anywhere, and `ZoneHead` under it was a `<span>`; the **three fiches**, where the ENTITY NAME — the largest text on screen and the answer to *what am I looking at* — was a div while the sections beneath it were real `h2`s, so a screen reader's heading list opened at « Les lots »; **all five forms**, whose outline was `h3, h3, h3` with no `h1`; and the **tasting setup**, three `SectionHead` `h2`s under a div hero. **`FormSection` moved h3 → h2 as a consequence, not as a preference**: with `FormScreen`'s hero now the `h1`, an `h3` skips a level — and it was checked first that no view combines `FormSection` with `SectionHead` (`TastingView` mentions it only in a comment), so the two cannot collide. **The RUNNING tasting stage deliberately gets NO `h1`**: its biggest text is the live timer, and a heading whose text changes every second is worse than none. **WHY NO CHECK CAUGHT IT, which is the durable part:** `a11y.curator.test.tsx` runs axe with `runOnly: ["wcag2a","wcag2aa","wcag21a","wcag21aa"]`, and **BOTH rules that would fire here — `page-has-heading-one` and `heading-order` — are tagged best-practice, so they are excluded by construction**; the file additionally disables `page-has-heading-one` on top of that, legitimately (views render as FRAGMENTS, where it fires per fragment). So the net is `headingStructure.test.tsx`, which is source-level for the same reason the layout gates are — rendering a fiche needs the whole ctx, and what rots is WHICH ELEMENT is used — with comments blanked first. It asserts the fiche `h1` contains the entity NAME rather than merely existing, and that `TastingView` has EXACTLY one. Probed: reverting the five sites reddens 5 of its 7 cases. **Every override is `fontWeight: 400` + `margin: 0`** so the rendered result is byte-identical — a browser's default `h1` is bold with a large margin, which is the whole reason these were divs in the first place.
- **Contrast**: every text/background color combination must hit WCAG AA. `oxbloodHi` was bumped to `#d27b6f` for that reason; `tx3` was raised to `#958e7a` (4.98:1 on `card`, 4.58 on `cardHi`) — it was the last sub-AA text in the app at 4.18:1 on `cardHi`. Still the tightest pair in the palette: flag for review before shrinking fonts or using `tx3` on `cardHi`.

## Font hosting — self-hosted woff2

Previously the app loaded Newsreader / DM Sans / IBM Plex Mono from `fonts.googleapis.com`. The app now ships the same fonts as static woff2 files under `public/fonts/` and removes the `fonts.googleapis.com` / `fonts.gstatic.com` whitelist from CSP. Rationale: one fewer third-party origin in the privacy story, no DNS hop for first paint, predictable cache lifetime via the existing SW.

- `index.html` declares the `@font-face` block inline (variable fonts for Newsreader regular/italic + DM Sans, static 400/500/600/700 weights for IBM Plex Mono) and preloads the two LCP-critical files via `<link rel="preload" as="font" type="font/woff2" crossorigin>`.
- `unicode-range` is set to Latin + a few diacritics so non-Latin scripts (none used today) don't pay the download cost if added later.
- `font-display: swap` everywhere — invisible-text flashes are worse than a brief unstyled flash.
- CSP `font-src` is now `'self'` only. Re-adding `fonts.gstatic.com` would silently re-enable a third-party request channel.
- The SW caches the woff2 files on first fetch (default cache-first behaviour applies, host is `'self'`).
- **If you swap or add a font file**: drop the woff2 in `public/fonts/`, add the `@font-face` declaration to the inline `<style>` in `index.html`, decide whether it warrants a `<link rel="preload">`, and run `npm run build` to confirm the bundle still emits the file under `dist/fonts/`.

## Viewport — pinch-zoom

`index.html` viewport meta is `width=device-width, initial-scale=1.0, viewport-fit=cover`. The previous `maximum-scale=1.0, user-scalable=no` was removed to let users pinch-zoom for accessibility (WCAG 1.4.4 Resize Text). Do not re-add `user-scalable=no` — locking zoom is an accessibility regression. iOS Safari's "tap to zoom on small inputs" is sidestepped via 16 px+ input font-size in the form primitives, not by disabling zoom.

**Reset on navigation.** `nav()` (App.tsx end of function) briefly swaps the viewport meta to a non-scalable form, then restores the original `content` in the next animation frame. The flip forces iOS Safari / Android Chrome to reset the visual viewport (zoom back to 100 %); the next-frame restore brings pinch-zoom back so the new screen is still zoomable. Without this, the user's zoom level persisted across screens — zooming into a card and then opening a form left the form at a weird zoom. The try/catch around the meta lookup protects against an unlikely missing tag.

### Clickable Stats — drill-down to filtered lists

Every chart and aggregate on the Statistics page is a one-tap entry point into its source list. The wiring lives in three layers:

**1. App-level state.** Three journal filters were lifted out of where they used to live in `JournalView`'s `useState` into `App.tsx` ctx so any view can pre-select them: `journalFilterPipe`, `journalFilterTobacco`, `journalFilterYear` + their setters. A fourth was added: `journalFilterDate` (ISO `YYYY-MM-DD`) for day-precise filtering from the calendar heatmap. Two more followed: `journalFilterCommune` / `journalFilterCountry` for the "Lieux" (location) stats click-thru. Two new pipe filters cover the bowl / stem material click-thrus: `pBowlMaterialFilter`, `pStemMaterialFilter`. All are reset on `nav()` like every other list filter.

**2. Navigation helpers** (App.tsx, mirror the existing `navToInvFiltered` / `navToPipesFiltered` shape — clear shadowing filters, set the targets, jump via `setView` not `nav()` so the new filter doesn't get wiped on the way):

- `navToPipesFilteredByMaterial(material, kind)` where `kind` is `"bowl" | "stem"`.
- `navToJournalFiltered(year, pipeId?, tobaccoId?)` for the year-level click-thru (monthly / yearly histograms — month label `"YYYY-MM"` is sliced to `"YYYY"` at the StatsView call site). Clears `journalFilterDate` so the two don't fight.
- `navToJournalFilteredByDate(date)` for the day-level click-thru from the calendar heatmap. Clears `journalFilterYear` (the date already implies the year) so the active-filter chip row stays uncluttered.
- `navToJournalFilteredByLocation(kind, value)` for the "Lieux" stats click-thru, `kind` ∈ `"commune" | "country"`. Sets just the chosen location filter and clears every other journal filter for a clean drill-down. JournalView surfaces each active location filter as a removable 📍 chip and AND-composes them in its session memo (strict `String(s.locationCity)` / `String(s.locationCountry)` equality). The "Lieux" section sits under the smoking-calendar heatmap in StatsView (it's session-derived).

**3. StatsView wiring** (`src/views/curator/StatsView.tsx`). Every clickable bar / cell carries an `item.onClick` callback (the chart primitives in `Charts.jsx` already supported this — no architectural change). The heatmap info line under the calendar transforms into a tappable button (`DD.MM.YYYY · N séances →`) when `calSel.count > 0`, calling `navToJournalFilteredByDate(calSel.date)`. Hover polish on `hBars` (Charts.jsx): the bar opacity bumps 0.88 → 1.0 on hover via inline `onMouseEnter/Leave` + a `data-hbar` selector; the label color already brightens tx2 → ivory for clickable rows (that predates this pass). Pure inline-style implementation, no CSS file.

**Year / date exclusivity invariant.** The journal's date and year filters are mutually exclusive on entry — setting one through the helper clears the other. JournalView's `sessions` memo still AND-composes both (so if a state-machine bug lets both through, the more restrictive wins) but the helpers enforce the cleaner UX. The Date chip surfaces at the very top of the JournalView (above the three regular dropdowns) so the user clearly sees it's the narrowest active filter.

**Tests.** `src/__tests__/statsClickthru.test.ts` locks the material AND-filter contract + the `"YYYY-MM" → "YYYY"` slice rule + the strict day-equality filter rule. `src/__tests__/curator/JournalView.test.tsx` was adapted with a stateful wrapper so `fireEvent.change`-driven assertions still work after the ctx-driven refactor (renderWithCtx doesn't run App.tsx so setters need real React useState behind them).
