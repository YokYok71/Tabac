## Two budgets, and the one nothing was measuring

**THE CELLAR SITS IN A QUOTA THE GUARD NEVER LOOKED AT.** `useStorageQuotaWarning` probes `navigator.storage.estimate()`, which reports the ORIGIN quota — what IndexedDB (the photo store) spends. The cellar lives in `localStorage`, whose ~5 MB sub-quota the StorageManager commonly does not account for; **the hook's own comment has conceded that for a long time, and what was never measured is how close a real collection already is.** MEASURED in Chromium by filling localStorage to failure: the ceiling is **5 200 000 chars**, a serious collector's cellar is **2 899 338** of them (**55.8 %**), and `estimate()` reports **0.112 %** of a 1049 MB quota **at the moment `setItem` throws**. The guard was watching a budget three orders of magnitude away from the one that fails.

**The consequence is not a refused write.** `save()` calls `setData(nd)` BEFORE `appStorage.set`, and the QuotaExceeded retry migrates INLINE photos — of which a modern cellar has none, they are already `local-photo-*` keys — so the edit stays on screen, looks saved, and **is gone on the next launch**. The error banner itself is fine (persistent, `role="alert"`, and tapping it opens Réglages → Données where the export is); what was missing was the warning BEFORE the cliff.

`LOCALSTORAGE_BUDGET_CHARS` (5 000 000, deliberately under the measured 5 200 000 — the ceiling is engine-specific and this number decides when a user is TOLD to back up) and the hook now warns on **whichever ratio is worse**, reporting the numbers that go with it: naming the milder of the two would understate the risk and point at the wrong remedy. **The origin probe STAYS** — it is the right measurement for the photo store, and the two budgets are independent. `cellarChars` is the length of the string `save()` was about to write, because re-stringifying inside the hook would double a cost measured at 13-15 ms on every data change; the load path seeds it from `r.value.length` so a first launch of an already-large cellar is measured before any save. **The payload check is no longer gated on the origin probe** — the effect used to `return` before doing anything when `storage.estimate` was absent, so on such a browser nothing at all was measured.

## Bundle budget, cold start and on-demand dictionaries

**THREE CHECKS MEASURE `dist/`, AND ONE VERIFIED IT WAS THE CODE.** `size:check`, `i18n:layout` and `theme:contrast` all judge the BUILT app, and only the first had learned that existence is not enough — a `dist/` older than `src/` gives a confident verdict on the PREVIOUS bundle. **The demonstration was on me**: two full `theme:contrast` campaigns measured an hour-old bundle, green throughout, which is how a stable 2566-element count became 2565 across a rebuild with no source change in between. Probed the obvious suspect first and it was innocent — the count is 2565 with and without `awaitMarker` — so the cause was the rebuild, not the checker. **A check reporting on the wrong artefact looks exactly like one reporting on the right artefact**, which is the whole failure mode. The rule now lives in `scripts/distFreshness.cjs` and all three call it; `distFreshness.test.ts` asserts each one consults it AND stops, and that none kept a local copy (a second implementation starts right and then only one of the two gets fixed — the drift this repo pays for in a loop). Two details worth keeping: tests are excluded from the walk (they never enter the bundle, so counting them would fail every test-only commit and teach people to route around the guard), and a FILESYSTEM error is tolerated while a `ReferenceError`/`TypeError` is rethrown — that means the guard itself is broken, and it did exactly that once, silently reporting OK on a stale bundle. `staleMessage` carries no check NAME, because two of the three callers funnel through a `die()` that already prefixes one and the first version printed « theme:contrast — theme:contrast: … ».

**Bundle-size guard**. `scripts/check-bundle-size.cjs` (`npm run size:check`) runs in the Lighthouse workflow **after `npm run build`, before the LHCI step** — a fast, deterministic pre-check that fails at build time with a clear message instead of after a 3-run Lighthouse pass. It parses `dist/index.html` for the eager script set (entry + static deps) and asserts their combined gzip stays under budget. **Why it exists**: a Lighthouse job once went red because a large body of data became EAGER (per-language prose merged into the entry chunk), and a chunk that loads on the home screen counts toward Lighthouse's `resource-summary:script:size` (500 KB hard cap) — eager JS hit 855 KB. It also REFUSES to measure a stale `dist/`, which is the failure that would otherwise report the previous bundle as current. Budgets are gzip transfer sizes, mirroring how Lighthouse measures.

**Cold-start catalogue gating (the reason changed, the RULE did not).** It was about a content-hashed JS chunk counting toward the eager script budget. There is no chunk — the catalogue is read from IndexedDB — so the cost is now an IndexedDB open plus a parse **MEASURED at 0.5-1.2 s for 1594 rows on a desktop, several times that on a phone** (see `catalogueStore`), which is worse on the home screen than a download would be. **The catalogue loads as ONE unit (REVERSING an earlier split — and there is only one unit to load).** That split had the fetch in two — a small specs chunk on form open, the 122 KB prose chunk only once a typed blend matched — and it was undone, because on an EXISTING tobacco the brand and name are already filled, so the match fires on the first render and the « synchroniser depuis le catalogue » offer appears ~1 s before the prose lands: tapping it inside that window synced every field EXCEPT `description`, which was therefore never saved, so re-opening the fiche offered the same update again. **React.lazy code splitting — narrow re-enable**. **EB chunk-load recovery**. Even with the cold-start guards above, a lazy chunk fetch can still fail later in the session — a stale SW cache after a deploy, a transient network blip on iOS Safari, etc. The error surfaces as `TypeError: Importing a module script failed.` (or `Failed to fetch dynamically imported module`), which used to land in the Error Boundary's generic "⚠ Erreur de rendu" UI with no way out. The EB in `App.tsx` now detects this error class via `isChunkLoadError(e)` (regex match on the message) and **auto-recovers**: unregister every SW, delete every `caches.*` entry, then `location.reload()`. The render path during recovery shows a sober "Récupération en cours…" / "Recovering…" screen instead of the harsh red error. **Anti-loop**: a `cave-eb-recovery-ts` timestamp is stamped in `localStorage` from `componentDidCatch` (single-call hook — `getDerivedStateFromError` can be called more than once per error in dev/Strict Mode, so the flag write MUST stay in `componentDidCatch`); if the same error hits again within 30 s the auto-purge is suppressed and the manual "Vider le cache et recharger" button is offered instead. A mount-only effect in App.tsx clears the flag if it's older than 5 min so a one-off failure doesn't permanently suppress future auto-recoveries. **What `purgeCachesAndReload` does NOT touch**: IndexedDB. `cave-imgs` (the photo store) is preserved across the purge — only the SW cache and SW registrations are wiped, which is the actual cause of the stale-chunk error. If you ever consider adding IndexedDB wipe to the recovery path: DON'T — that would nuke every local photo, which is a far worse outcome than re-fetching JS. Tests in `src/__tests__/EB.test.tsx` lock the three render branches (legacy unrelated error, chunk first hit → recovering UI, chunk repeat within 30 s → manual UI) + the manual retry button.

**Cold-start shell pattern**. `data` initialises to `INIT` (empty inventory) instead of `null`, and the top-level `if (loading) return <pipe-icon/>` early return in `App.tsx` was removed. The shell (TopBar + Dock + empty HomeView) renders the instant the React mount completes; a fixed-position loading veil mounted inside `CuratorApp.tsx` covers the inner viewport area (max-width 600 column) until `loading` flips to `false`. Two invariants:

**i18n ON-DEMAND dictionaries (replaces the eager chunk).** Only **English** is statically imported by `src/i18n.ts`; `fr`/`es`/`de`/`it` are reached through `import.meta.glob("./i18n/*.ts")` and fetched on demand, each its own content-hashed chunk. **Cold start 303.2 → 240.5 KB gzip**, and the eager budget went from ~29 KB of headroom to 91.5 — which is what makes a sixth language possible (it was the documented blocker). **The three rules**: (1) the phone's language wins — `detectUiLang` is unchanged; **The four failure states that change created and did not handle.** A follow-up audit found them; each was reproduced before being fixed, and each is probed to fail on the old code (`i18nOnDemand.test.ts`). (1) **A failed switch cannot be retried in-session, and the copy said to do exactly that.** A dynamic `import()` that fails is cached AS A FAILURE in the browser's module map, so re-importing the same URL re-throws with NO network request — MEASURED in Chromium: tap offline → reconnect → tap again = **one** request in total, both attempts fail; only a reload clears it. `ensureLang` is otherwise written to be retry-friendly (no sticky `failed` flag, `inflight` cleared in `finally`), which is what made this invisible. `lang_offline_err` now names the reload, and the notice carries the button. **Do not "fix" this by clearing a flag — the state is in the browser, not in this module.** (2) **`EB.tsx` fell back to `LANG.fr`**, which is `undefined` unless French happened to load — so the string table collapsed to `{}` and every label dropped to its hardcoded French literal, in precisely the case an error boundary exists for (a chunk that failed to load). A German user with German unloaded read "⚠ Erreur de rendu". Now `LANG.en`, and its `cave-lang` default is `"en"` like App.tsx's. The four `(LANG as any)[_lng]?.key` storage-error strings in `App.tsx` route through `LANG.en` for the same reason. (3) **The STARTUP failure was invisible**: `main.jsx` mounts whether or not `ensureLang` resolved true, so `lang` stayed on the stored code while `translate` served English — English UI, DE highlighted in the picker, no notice. (4) **Concurrent switches resolved by network timing**: tap DE (slow) then IT (fast) and the DE response landed last and won. `saveLang` carries a generation counter (`langGenRef`); a superseded resolution returns early, which also stops it clearing the spinner while a later fetch runs. **Cross-platform package-lock gotcha.** Vite 8 + Rolldown + `@vitejs/plugin-react` 6 pulls in lightningcss, `@oxc-parser`, `@oxc-resolver`, `@rolldown/binding-*` — each declares ~15 platform-specific bindings under `optionalDependencies`. ### After every build — mandatory checklist

After every code change that bumps `APP_BUILD`, you **must** update the following before committing:

1. **`src/constants.ts`** — bump `APP_BUILD` to the new number.
2. **`public/version.json`** — set `build` to the new build number and `version` to the current app version. Its `generation` must equal `APP_GENERATION` (doc:check enforces it) — leave it alone unless you are deliberately renumbering the version downward, in which case bump BOTH in the release that PRECEDES the renumber. This file is fetched by `checkVersion()` to detect available updates. **Never forget this — omitting it breaks the update check.**
3. **`package.json`** — when bumping `APP_VERSION`, also bump `"version"` (semver form: e.g. `1.0.0` for APP_VERSION `1.0`). The two MUST stay aligned — `doc:check` will fail otherwise.
4. **`public/changelog.html`** — **MOST BUILDS ADD NOTHING HERE.** Add an entry only if this build shipped a new feature, a new setting, or a behaviour change a user would both NOTICE and ACT on. If you find yourself describing a colour, a border, a photo, a font size, a load time, a bundle, a translation that was missing, or something that used to be broken and now works — **write no entry**. A fix-only bump is expected to leave this file untouched: `doc:check` lets the latest entry LAG behind `APP_BUILD` precisely so nobody has to invent one. When an entry IS warranted, add it at the top of **each** language section (`sec-fr` / `sec-en` / `sec-es` / `sec-de` / `sec-it`) under the current version subtitle, and fetch the current file from GitHub first (`mcp__github__get_file_contents`) to avoid stale edits. **Gate 12 of `doc:check` now enforces this**: an entry sub-titled `Correction` / `Fix` / `Corrección` / `Behoben` / `Correzione` FAILS the check, and display/implementation vocabulary raises a warning to triage — see the `### changelog.html rules` section in `CLAUDE.md`.
5. **`public/help.html`** — update the relevant sections (one per UI language: fr/en/es/de/it/pt) if the change affects documented behaviour (new UI, renamed fields, changed logic). Fetch from GitHub first.
6. **`npm run doc:check`** — must exit 0 before commit. The script cross-checks `APP_VERSION` / `APP_BUILD` / `version.json` / `package.json`, asserts the latest changelog entry's build number is **≤** `APP_BUILD` (loosened from `=` post-— a fix-only bump should not force a fake changelog entry; the `### changelog.html rules` section in `CLAUDE.md` forbids logging simple fixes), every `src/utils/` and `src/hooks/` file mentioned in CLAUDE.md, every localStorage key documented in the keys table, and i18n integrity (every `t("…")` call site resolves in the `fr` reference dictionary, and every discovered `src/i18n/<code>.ts` — fr/en/es/de/it/pt today — carries exactly the same key set as `fr`). Two anti-drift gates: (a) **privacy disclosure** — every third-party domain referenced via `https://` literals in `src/` (minus the placeholder / user-tapped-link hosts in `DOMAIN_IGNORE`) must be disclosed in `public/privacy.html`, verbatim or via a `DOMAIN_EVIDENCE` prose mapping ("Anthropic" for `api.anthropic.com`); adding a new fetch target therefore forces a privacy edit in the same commit — this gate would have caught the corsproxy.io / allorigins.win omission it was written for, and DID catch the undisclosed cdnjs.cloudflare.com (JSZip CDN) the day it landed. (b) **structure tree** — every concrete path in the CLAUDE.md "## Repository Structure" fenced tree must exist on disk (glob entries skipped); renames and deletions can no longer leave ghost files in the doc. A non-failing **test-count freshness** check counts the `*.test.*` files + static `it()`/`test()` cases and WARNS (never fails — it's a "~" approximation) when the documented "~N tests across ~M source files" figures (Tech Stack table + Key Conventions #5) drift past tolerance (±10 % files / ±20 % cases), so the hand-maintained figure gets a nudge instead of silently rotting. The file count is the reliable anchor; the static case grep necessarily under-counts vs Vitest (`.each` / property tests expand at runtime).

Documentation-only changes (help, changelog, CLAUDE.md) do **not** require bumping `APP_BUILD` — but the changelog rule about every entry living in EVERY language section (fr/en/es/de/it/pt today — `docParity` derives the list from `LANGUAGES`, so a sixth section is not optional) still applies.

**`doc:check` enforces the bump.** The script now scans every commit between the last `APP_BUILD` bump and `HEAD`. If any user-visible file (`src/views/`, `src/hooks/`, `src/utils/`, `src/components/`, `App.tsx`, `i18n.ts`, `constants.ts`, etc. — full list in `scripts/doc-check.cjs`) changed without a subsequent bump, the script fails with the offender list. This catches the failure mode where multiple user-visible commits ship to `main` without anyone realising the version display in Settings still reads the previous build.

**THE ESCAPE HATCH, AND THE RULE FOR TAKING IT.** It used to read *"`DOC_CHECK_SKIP_BUMP=1`. Use it ONLY when the staged batch is genuinely runtime-neutral"* — a clear rule, in this file, **broken twice in one session**, both times identically: the gate printed the offending files, the failure message offered the hatch on the very next line, and the hatch was taken **without the diff ever being opened**. Two things made that easy and neither was a comprehension problem. **(a) The guard is enforced NOWHERE.** `deploy.yml` and `checks.yml` both set `DOC_CHECK_SKIP_BUMP: "1"` unconditionally — legitimately, for a DIFFERENT reason: on a branch that has not bumped, comparing against the last bump commit is meaningless, and the CI checkout is shallow. So the only enforcement is a human running it locally, which is exactly what failed — the "a gate in a parallel workflow cannot block a deploy" shape, one storey further out. **(b) The hatch cost nothing to reach for.**

**So it is a mechanism now, not a sentence** (`docChecks.resolveBumpSkip`, 8 cases): a bare `1` is accepted **only when `CI` is set**, and a human must **NAME the flagged files** — `DOC_CHECK_SKIP_BUMP='src/utils/x.ts,src/views/y.tsx'` — with the names matching the computed set EXACTLY, so an incomplete list, a stale one, or a plausible-looking guess are all refused. You cannot produce that list without having read the one the gate just printed, which is precisely the step that was skipped. **It is an ACKNOWLEDGEMENT, not a correctness check** — it cannot know whether a diff is really runtime-neutral — the same shape as `// scope-ok:` and `// lang-axis-ok:`. An EMPTY offender set short-circuits silently: complaining about a redundant flag when the gate would not have fired is the over-strict mistake that gets guards routed around.

**THE RULE, in order, and the judgement is still yours:** (1) run `doc:check` with NO flag and read the file list it prints; (2) for EACH named file run `git diff <lastBumpSha>..HEAD -- <file>` and look at the hunks — **from the diff, never from memory of what you changed**; (3) the hatch is permitted only if EVERY hunk is a comment, a type annotation, a test, or a deletion with no remaining caller — anything touching a string, a number, a style value, a default or control flow is user-visible; (4) it is **per BATCH, not per file** — two qualifying files and one that does not means BUMP; (5) **when in doubt, BUMP.** The bump is two lines and needs no changelog entry (most builds add none, and the version gate deliberately lets the latest entry lag), whereas shipping user-visible change under a stale build number means `checkVersion` never fires and the dictionaries — which travel in content-hashed chunks — never reach anyone. **The bump IS the delivery mechanism.** The gate's failure message no longer advertises the hatch as an alternative, and the two workflows keep theirs.

**`doc:check` enforces i18n parity (generalised to N languages).** The dictionaries are split per language: `src/i18n/fr.ts` (`export var FR`), `src/i18n/en.ts` (`export var EN`), `src/i18n/es.ts`, `src/i18n/de.ts`, `src/i18n/it.ts`, one `key:"value"` per line, registered in `LANG` by `src/i18n.ts` (English statically, the rest on demand — see the structure-tree entry). `fr` is the reference/canonical key set. Every key used as `t("…")` in `src/` (outside tests) must exist in the `fr` reference, AND every auto-discovered `src/i18n/<code>.ts` must carry EXACTLY the reference key set. Adding a key to one language and forgetting the others is the most common i18n bug. The check parses every `.ts` / `.tsx` / `.js` / `.jsx` file under `src/`, extracts literal keys passed to `t("…")` via regex, then cross-references against every dictionary (which it parses directly for `key:"value"` pairs — the **no-space-after-colon** shape is required by that regex, so keep it). Missing keys fail CI (exit 1); keys defined in i18n but never called are reported as warnings only (they may be referenced indirectly via `xl()` or future-proofed). **Dynamically-built keys**: keys resolved via `t(prefix + var)`, a map lookup, or `L.<key>` property access (class components like `EB.tsx`) are invisible to the literal-`t("…")` scan, so they'd surface as false "never called" noise. `scripts/doc-check.allowlist.json` carries `dynamicKeyPrefixes` / `dynamicKeys` to suppress them, keeping the unused-warning at ~0 so a genuinely-new dead key stands out. **CONVENTION — when you introduce a new dynamic-key family** (a new `t(prefix + …)` group, a new enum→`maint_kind_*`-style map, a new `L.<key>` set), **add its prefix to `dynamicKeyPrefixes` in the same commit** — otherwise every member reappears in the unused warning and erodes the signal.

**`doc:check` also enforces dev-fallback parity (gate (b.2)).** The ubiquitous `t ? t("key") : "French fallback"` idiom carries a literal that NEVER renders in production (`t` is always present) — but a drifted fallback is misleading and would show wrong text in any `t`-less render path or test. The gate scans `src/` (outside tests + the dicts) for `t("key") : "literal"` and **fails** if the literal isn't byte-identical to `fr[key]` (raw/escaped form, matching how `parseBlock` stores the reference). A one-time sweep reconciled 129 pre-existing divergences (stale "Drive"→"cloud" rename, `…` vs `...`, casing, shortened labels); the gate keeps the class dead. **When you add a `t ? t("k") : "…"` site, the fallback must equal the `fr` value verbatim** (emoji, punctuation and all) or doc:check goes red.

  **It is measured as GEOMETRY against the real clipping boundary, never as an element's own `scrollWidth`** — the leaf carries the text, the ANCESTOR decides whether the overflow is reachable. For each text LEAF the walk goes up to the first ancestor that settles the question: `auto` / `scroll`, or a `data-hscroll` marker, means the content is reachable by dragging and therefore belongs to the scroller rule, so those **CLEAR** the element instead of accusing it; `hidden` / `clip` is the clipping boundary, and the leaf's right edge is compared against `cr.left + clip.clientLeft + clip.clientWidth` (`clientLeft` skips the border, `clientWidth` excludes it and any scrollbar). **Leaves only, and only leaves with TEXT**: a decorative gradient bleeding out of a rounded `overflow: hidden` card is the intended use of that property, and reporting it would be the over-strict mistake this file keeps recording — what is never intended is a WORD cut in half.

**The three blind spots a four-agent audit surfaced, and the one shape they share.** A parallel read-only audit (four lenses: tool coverage / cross-site consistency / theming / i18n-outside-JSX) produced ~22 findings, every one I re-verified turning out real. Three were systemic, and all three are the SAME shape as the `.jsx` and `prune` gaps: *a guard covers one channel, one folder, or one data path, and everything outside it is presumed clean because nothing looks at it.*

1. **THE GATES DID NOT EXIST.** `npm run typecheck`, `npm run lint` and `npm run prune` were in **no workflow at all** — CI ran only `npm test` / `build` / `doc:check` / `size:check`. **Prototype-safety rule (`"error"`).** `tabac-local/no-dynamic-index-plain-map` (`eslint-rules/no-dynamic-index-plain-map.cjs`) consolidates the finding class that audit rounds 8-12 kept surfacing ONE site at a time (`resolveCanonicalBrand`, `computeAgingSweetSpot` maps, `AccListView`/`AccessoryDetailView` `TYPE_COLORS`/`TYPE_ICONS`, `TrashModal` `KIND_*`, `THEMES`, `DOC_PAGES`, `toggleCollapseKey`…). It flags a DYNAMIC (non-literal) computed index `M[expr]` into a MODULE-LEVEL `const` plain-object lookup map whose KEY type is runtime-forgeable — `Record<string, …>`, `Record<any, …>`, a `{ [k: string]: … }` index-signature literal, or no annotation. On a plain object a key equal to a prototype member (`"__proto__"`, `"constructor"`, `"toString"`…) resolves to the value on `Object.prototype` — a truthy non-value that defeats the ubiquitous `M[key] || fallback` guard. The fix is a null-prototype map: `Object.assign(Object.create(null), { … })` (or `Object.create(null)` for a mutable one). **Deliberately NARROW to keep false positives ~0**: (1) module-scope `const` only (a local `{}` accumulator is a different animal); (2) the initializer must be a bare `ObjectExpression` — the null-proto forms + `new Map()` are recognised and skipped; (3) **closed-union-keyed maps are SKIPPED** — `Record<MaturityChipSize, …>` / `Record<IcoName, …>` / `Record<WatchKind, …>` can only be indexed by a value TypeScript already proves is in-set, so they're not prototype-forgeable AND wrapping them would also drop the object literal's exhaustiveness check (the rule reads the key type off the declarator's TS annotation to tell the two apart); (4) WRITE targets (`M[k] = v`) and `delete M[k]` are skipped. Escape hatch: `// eslint-disable-next-line tabac-local/no-dynamic-index-plain-map` for a map whose keys are a provably-closed safe set the rule can't see. Self-test: `src/__tests__/eslint-no-dynamic-index-plain-map.test.ts` (14 cases). **When you add a module-level lookup map indexed by a data-derived string, build it null-proto from the start** — the rule will otherwise block CI.

**NARROWING (1) — "a local `{}` accumulator is a different animal" — WAS WRONG FOR THE CASE THAT MATTERED, and it cost the harshest failure this app can produce.** `ghosting.ts` builds FOUR function-local accumulators, two keyed by `tobacco.id` and two by `tobacco.category`, and `migrateData` coerces a category to a string without ever validating it against `CATS` — so a JSON import or a cloud restore carries `category: "__proto__"` straight in. `counts[cat] = (counts[cat] || 0) + 1` then reads `Object.prototype` (TRUTHY, so `|| 0` never fires), writes through the `__proto__` SETTER (which ignores a non-object, so the key is never stored), and leaves `total` at 1 with `Object.keys(counts)` empty — `families[0].count` throws. **THAT THROW IS A BRICK, NOT A GLITCH**: `CuratorApp` mounts `CuratorPipesListView` unconditionally and its `pipeFamily` memo sits ABOVE the view's own early return (the hook-order rule REQUIRES it), so it fires on the first render after `data` loads **whatever screen the user is on**; `_runImport` calls `save()` before any render, so the row is already on disk; the error boundary replaces the whole tree, so Settings — and « Effacer toutes les données » — is unreachable; and **neither recovery path clears localStorage** (`EB.purgeCachesAndReload` and `public/reset.html` both stop at service workers and Cache Storage). The only way out is clearing site data or deleting the PWA, with the user's own cellar stranded. **Hex-alpha rule (`"error"`).** `tabac-local/no-hex-alpha-concat` (`eslint-rules/no-hex-alpha-concat.cjs`) forbids concatenating a 2-hex-digit alpha suffix onto a colour. Before theming, `C.brass + "22"` produced a valid 8-digit hex; varizing the palette turned the token into `var(--c-brass, #d4a661)`, so the same expression now yields `var(--c-brass, #d4a661)22` — **not a colour, and browsers drop an invalid declaration silently**, leaving no background / no border and no error anywhere. The replacement is `alpha(token, "22")`. **Why it needed a rule and not more discipline**: the migration swept this class, CLAUDE.md documented it in two places, and a later audit agent explicitly CLEARED the category — and five live sites were still shipping (MaturityChip background + `sm` border, AICard card + button borders, AgingBadge background + border). Each survived because every sweep grepped ONE spelling; the shapes actually in the wild were `token + "22"`, `token + (c ? "22" : "1c")`, `` `${token}22` ``, `` `${token}${c ? "55" : "25"}` `` (split across two interpolations — invisible to a `${C.x}AA` grep, which is why it lived longest) and `colour + someLocalConst`. MEASURED in Chromium before the fix: every maturity chip rendered at `backgroundColor: rgba(0,0,0,0)`. The rule is **positional, not value-based** — it asks whether a 2-hex string sits in a concatenation slot, and deliberately does NOT judge whether the receiver "looks like a colour" (that judgement is what the greps got wrong). It resolves a local `const` to its initializer, because the AgingBadge instance hid behind exactly that indirection and a literal-only first version stayed green on it. Scoped to the design-system files (same set as the no-hex / no-raw-fontSize selectors). Self-test: `src/__tests__/eslint-no-hex-alpha-concat.test.ts` (21 cases; all five real shapes pinned as invalid fixtures, plus `${x}ffset` as a valid one so the word-boundary guard can't be dropped). `MaturityChip.test.tsx` carries a runtime counterpart asserting the rendered `background` is a `color-mix()`.

**Focus rule (`"error"`).** `tabac-local/no-scrolling-focus` (`eslint-rules/no-scrolling-focus.cjs`) requires `{ preventScroll: true }` on every `.focus()`. **Why it needs a rule and not discipline: the defect is invisible in BOTH engines this repo can run.** jsdom does not lay out or scroll at all; and Chromium focuses a `div[tabindex=0]` on tap — so a focus restore lands back on the row — and treats `document.body.focus()` as a no-op. **iOS Safari does neither**: it does not focus non-form elements on tap, so `Modal`'s recorded "last active" element is `<body>` there. A bare `.focus()` can therefore be added, measured green in every harness available here, and still lose the user's place — which is exactly how one half of a two-part report came to be declared sound on the strength of a Chromium run. Flags a member call ending in `.focus` with no argument, or with an object argument lacking `preventScroll: true` (an options object that says nothing is the shape a half-applied fix leaves behind; `preventScroll: false` is flagged too, so asking to scroll gets a reason attached via the disable comment). A variable or spread argument is ACCEPTED — the rule cannot see inside it and guessing produces the false positives that get guards switched off. **OFF in `src/__tests__/**` and `scripts/**`**: a `.focus()` there SIMULATES what the browser does when a user taps or tabs, and the browser scrolls, so opting out would model something that never happens. Self-test: `src/__tests__/eslint-no-scrolling-focus.test.ts` (19 cases, incl. the wiring and both exemptions). **Its first run flagged 13 sites, every one in tests or scripts and none in production** — the rule confirming the sweep was complete.

**Lot-scope rule (`"error"`, two files only).** `tabac-local/no-unscoped-lot-read` (`eslint-rules/no-unscoped-lot-read.cjs`) flags EVERY `.lots` read in `InventoryListView.tsx` + `InventoryDetailView.tsx` unless it carries a `// scope-ok: <reason>` comment. **Why a rule at all**: when the list is filtered to a lot-level slice, every figure on the card and the fiche must describe the lots in that scope — that leak was fixed seven times and the final systematic sweep still found five more sites, two of them SORT ORDERS (invisible as text, so unreachable by fixing what the user could see). The discipline was then written into CLAUDE.md as prose, which is exactly the state in which the five leaks existed: nothing enforced it. **It is deliberately dumb — an ACKNOWLEDGEMENT rule, not a correctness rule.** It makes no attempt to judge whether a given read is correctly scoped: that judgement is the thing a human keeps getting wrong, and a clever rule that guessed would either miss the interesting cases or force correct code to be rewritten to please it (an over-strict guard is worse than none, because it gets correct work deleted). Same philosophy as the label contracts: force a conscious re-read at the moment someone touches lot-derived data. **The annotation attaches to the ENCLOSING STATEMENT** (the comment block directly above it, or a trailing comment on the read's own line), NOT a line window — the first version matched within 3 lines and a probe (inject a leak into the real view, expect red) showed a new unscoped read placed right below an annotated one silently inheriting its license. One statement, one acknowledgement; a contiguous run of `//` lines is one annotation so a long reason needs no reflowing. Writes (`tob.lots = …`, `delete`) and object-literal keys are skipped; computed `tob["lots"]` is flagged. Self-test: `src/__tests__/eslint-no-unscoped-lot-read.test.ts` (15 cases, incl. that false-negative case and an assertion that the rule stays WIRED to both views and isn't file-disabled). **Eight reads are annotated today** — the chip counts (they label the filter chips themselves, so they must see every lot), the two `scopedLots` scope routes, the deliberately-unscoped `nFinished` / `finishedCount` (both consumers are gated on there being no scope), the lot list (`visibleLots`, whose second filter IS the scope), and the raw `indexOf` the store mutations key on. **When you add a figure to either view, route it through `lotInScope` / `scopedHeldWeight` / `scopedOldestAgeDays` — or say in one line why it doesn't need to.**

**Enum-render rule (`"error"`).** `tabac-local/no-raw-enum-render` (`eslint-rules/no-raw-enum-render.cjs`) enforces the enum DISPLAY invariant (see that section) in the Curator source: a bare `{item.category}` rendered as JSX TEXT is flagged; it must go through `xl(value, XXX_EN)`. **Why it needs a rule**: the stored value is canonical FRENCH, and it usually reads fine in English too (`Ribbon`, `Flake`, `Billiard`), so the leak is INVISIBLE to anyone testing in fr or en while showing French to es/de/it — which is how SIX sites shipped at once (tobacco card + detail category·cut, Home featured tobacco and pipe, pipe-detail shape header, accessory-card fuel, every SearchModal subtitle). Every current site is correct, so it ships at error level. **The rule asks "is this value rendered as text?" and every step of the walk from the read to the JSX container must be a rendered position** — that inversion is what stopped it misfiring: a CallExpression ARGUMENT is never rendered (the call's RESULT is), which silences `xl(v, CATS_EN)`, the local alias `tr(v, SHAPES_EN)` in `PipesDetailView`, and the colour lookups `catColor(fam.category)` in ONE rule instead of three hand-written excuses — an excuse-list version flagged two of them wrongly. Skipped: JSX **attributes** (`<SelectField value={form.category}>` MUST pass the canonical value or the option stops matching and the save breaks; `key=` wants identity), the left operand of `&&` (a guard — but NOT of `||`/`??`, where the left IS what renders: `{tob.cut || "—"}` is flagged), a conditional's test, statements inside a `.map()` callback (only its returned value renders), and the `{xl ? xl(v, X_EN) : v}` dev-fallback idiom. Caught: the bare read, both halves of `{cat} · {cut}`, template literals, a HALF-translated line (`{xl(p.shape, SHAPES_EN)} · {p.finish}`), and `map(f => f.category)`. Verified by re-injecting two of the real leaks into `AccListView` and `PipesDetailView` and confirming both go red. Self-test: `src/__tests__/eslint-no-raw-enum-render.test.ts` (22 cases, incl. the two false positives as permanent fixtures + a check that the field list covers every translated enum). **When you add a translated enum to `ENUM_TRANSLATIONS`, add its field name to `ENUM_FIELDS` in the rule** — a field missing there is silently unguarded.
