## The catalogue is the user's own file

The app once SHIPPED a reference catalogue — 1594 blends by the end, researched and reviewed over a dozen deliveries, emitted as a content-hashed specs chunk plus one lazy prose chunk per language. **It is gone.** That catalogue was the author's own work and not general-purpose data, so rather than ship one to everybody the app now ships the MECHANISM: Réglages → Données → *Catalogue de référence* offers a CSV template, loads a file the user fills in, keeps it in IndexedDB, and lets them export or remove it.

**What left the repo.** `src/data/` in full (`tobacco-db.master.csv`, the generated `tobacco-db.json`, the six `tobacco-db.desc-<lang>.json`), plus `scripts/import-tobacco-db.cjs`, `validate-tobacco-db.cjs`, `translate-tobacco-db.cjs`, `catalogue-load.cjs` and `export-tobacco-db-xlsx.cjs`. **None of it is recoverable** — the per-row sourcing journals in particular, which recorded which source settled which field. That was decided knowingly; do not go looking. **What this file keeps is the reasoning** (the coherence-checker section, the enum-mapping rules, the aging-constant arbitrations): those decisions still govern the checker and the browser parser, and deleting them would lose the *why* while keeping the *what*.

**The consequence every caller must respect: `loadTobaccoDb()` resolving `null` is the ORDINARY state of a fresh install, not a failure.** The failure-kind apparatus (`isChunkFailure` / `tobaccoDbFailKind` / `tobaccoDbRetry`) went with the chunk it described — and it had to, because it was not merely unused but MISLEADING: it offered a reload for a download that no longer happens. `CatalogueMissing` replaced the old chunk-failure screen on the three views that render it (the Catalogue page and both entry forms, under the brand field), and the same reasoning reached the bulk catalogue pass and — as a message rather than a banner — the AI auto-fill's «no match» error. Each names the remedy instead of offering a retry.

**What still exists and why.** `utils/userCatalogue.ts` parses the CSV and **must keep normalising exactly the way the removed Node importer did** — a catalogue whose cut says `Zigzag Cut` is one the app half-understands (no `CUT_DENSITY`, no `xl()` translation, no dropdown option, so opening and saving that tobacco REWRITES the user's cut). **The example was corrected in both places: it used to read `Krumble Kake`, which `CUT_MAP` sends to `Crumble Cake` and the app therefore understands perfectly** — the illustration named the one case the import contract exists to handle. Caught by writing a test fixture from it and watching the assertion fail. That agreement was a live cross-check against the importer's own output; it is now the frozen fixture `src/__tests__/fixtures/catalogue-excerpt.{csv,expected.json}` — 20-odd real rows with the exact output the importer emitted for them. `utils/catalogueStore.ts` owns IndexedDB; `hooks/useUserCatalogue.ts` owns the Settings section. The Node checker did NOT survive — it was deleted a few releases later along with the rest of the catalogue tooling; what judges a catalogue now is the in-app report (Réglages → Données → « Vérifier mon catalogue »). See the tombstone section.

**THE FIXTURE IS SYNTHETIC, and that is the last step of the removal.** `src/__tests__/fixtures/catalogue-excerpt.{csv,expected.json}` once held ~20 rows lifted VERBATIM from the shipped master — real prose in six languages plus the `reviewValidated` sourcing journal, 160 KB of the author's own research, public on GitHub. It is now 30 INVENTED rows (15.6 KB). What the substitution preserved is not the data but the STRUCTURE each test exercises, and the fixture's own header names them one by one: a multi-blend brand with a distance-1 typo and a prefix-unique blend (Halvorsen), punctuation tolerance (R.T. Mallow), `&`/`and`/glued plus a short alias (Marlow & Finch), numeric blend aliases (Vondel), the merged row whose retired names survive as aliases (Aldwych), accent folding on a BRAND (Østergaard) and on a BLEND (Rivière Dorée), and tokenised search (Corvane). **Two consequences are recorded rather than hidden.** (a) The expected side is now a re-derivation of what this parser produces, where it used to be the deleted Node importer's frozen output — that non-circularity is gone, but so is the importer, so the comparison it protected had already lost its second term; it remains a regression lock. (b) `catalogueMergedAlias.test.ts` LOST a case — it pinned editorial CONTENT of the merged row's six proses, including a negative assertion enforcing a retracted Syrian-Latakia claim. With the prose synthetic that case has no subject, exactly like the three removed with the Node tooling, and rewriting it against the generator's template would assert the generator. The four structural cases around it survive. **The app's form placeholders and the downloadable CSV template moved to the same invented names**, so nothing on screen points at a catalogue that is no longer anyone's. **Two things a future reader should not have to rediscover.** The excerpt is the fixture EVERY lookup test loads (`src/__tests__/catalogueFixture.ts`), so "a catalogue is loaded" is now something a test supplies rather than gets for free — and its rows were chosen because the suite names them, not because they were convenient. And the cases that could not be reproduced from 20 rows were made SYNTHETIC rather than deleted: the brand-versus-alias precedence is now a two-row CSV built to collide, which is stronger than the original, since that one depended on the key order of a file the repo no longer controls (probed: reverting to a single resolution pass reddens it).

## AI Integration

The AI auto-fill feature (`useAiAutoFill` hook, exported as `aiAutoFill()`) supports three providers, selectable in ⚙️ Settings:

| Provider | Default model | API key source |
|----------|--------------|----------------|
| Anthropic (default) | `auto` → `claude-haiku-4-5` | console.anthropic.com |
| OpenAI | `auto` → `gpt-5.6-luna` | platform.openai.com |
| Google Gemini | `auto` → `gemini-3.5-flash-lite` | aistudio.google.com |

- **Model selection:** the model is user-selectable per provider in Settings → AI → "Modèle", persisted in `ai-model-<provider>` (defaults above). `useAiAutoFill` exposes `aiModel` / `saveAiModel` + the curated `AI_MODEL_OPTIONS` map (Anthropic: Haiku 4.5 / Sonnet 5 / Opus 5, cheapest first, **exact model ids with NO date suffix**; OpenAI: GPT-5.6 Luna / Terra / Sol; Gemini: 3.5 Flash-Lite / 3.6 Flash, cheapest tier first, no Pro tier because the current Gemini Pro is preview-only). The model id flows into all four request sites (`buildScanRequest` takes a `model` param; the autofill anthropic/openai bodies + the Gemini URL via `geminiUrl(model)` use `aiModel`). `saveAiProvider` recalls the new provider's saved model. `allowed_callers: ["direct"]` stays on ALL Anthropic models — mandatory on Haiku, harmless on Sonnet/Opus. **Legacy-id normalisation:** the chosen id is persisted per provider FOR EVER, so refreshing the list above would otherwise leave a returning user pinned to a superseded id with no visible cue (the Settings picker keeps an off-list value selectable and renders it as its raw id). `AI_MODEL_ALIASES` + the pure `normalizeAiModel(id)` map a stored legacy id onto the current option ON READ (initial state, `saveAiProvider`, and `saveAiModel` — no migration write): `claude-haiku-4-5-20251001` → `claude-haiku-4-5` (dated snapshot → canonical) and `claude-opus-4-8` → `claude-opus-5` (same price + 1M context). **Only same-price / same-context successors may be aliased** — an alias must never surprise the user with a costlier call. The map is null-prototype (the key comes from stored data). Locked by the "AI model catalogue" block in `useAiAutoFill.test.ts`, which also asserts every alias TARGET is a real option and no alias SOURCE is still offered. `public/help.html` deliberately names model FAMILIES only (Haiku / Sonnet / Opus), never versions, so a catalogue refresh can't make the help text false. **The OpenAI + Gemini lists were RETIRED UPSTREAM, not merely dated**: `gemini-2.0-flash` (the hook's Gemini DEFAULT) was shut down 2026-03-03 and `gpt-4o`/`gpt-4o-mini` left OpenAI's model list, so every Gemini auto-fill was failing outright. Both lists moved to the current families and all six dead ids are aliased. That forced a SECOND kind of alias, and the distinction is documented at the map: a **same-tier** successor preserves price + context (the Anthropic pairs), while a **retired** model has no price-preserving option left (the request 400s) so it maps to the nearest CURRENT tier, favouring the cheaper one — prices moved upstream and no alias can undo that. **Never alias a LIVE model to a costlier one.** A test asserts no alias crosses provider families (an OpenAI id sent to Anthropic would 404 cryptically). **`openaiMaxTokensField(model, n)`** is the other half of the OpenAI move: GPT-5 and the o-series **reject `max_tokens`** on Chat Completions ("Unsupported parameter … use 'max_completion_tokens'"), so switching the list without switching the field would have 400'd every OpenAI request; legacy 4o-era ids keep `max_tokens`. Applied at BOTH OpenAI request sites (autofill body + `buildScanRequest`) and locked per-site. The Gemini wire shape is unchanged and still correct (`v1beta/models/<id>:generateContent`, key in `x-goog-api-key`). **`AI_MODEL_AUTO` ("auto"), the delegated choice and the new DEFAULT for fresh installs.** It is offered FIRST in every provider list and is a SENTINEL, never a wire value: `resolveAiModel(provider, stored, dead)` (pure) turns it into the cheapest CONCRETE curated tier at request time, and the 4 request sites use that resolved id (`effModel` in `runAutoFill`, `scanModel` in `aiScanLabel`) — a literal `"auto"` on the wire would 404, so a test asserts the resolved id reaches fetch and that `resolveAiModel` NEVER returns the sentinel. **It deliberately does NOT query the provider's model-list endpoint**: those return embeddings / TTS / moderation / fine-tunes with no reliable "good at this task" metadata, cost a request on the happy path, and could land on a frontier model — spending the user's money on a choice they never made. What auto buys instead is (a) a list refresh moves the user forward instead of stranding a frozen id, and (b) **self-healing**: a model retired upstream is recorded in `ai-model-dead-<provider>` (`deadModelsKey`, capped at 8, corrupt value degrades to "nothing is dead") and skipped from the next call on, so a retirement costs exactly ONE failed call ever — which is how the four-month Gemini outage would have healed itself. Under auto the error copy is `ai_err_model_auto` ("un autre sera utilisé, relancez la recherche") since there is nothing to reconfigure; a PINNED model keeps the actionable `ai_err_model_gone` and records nothing — the user asked for that model, so they must see the real error rather than a silent substitution. Settings names the resolved model under the picker (`aiModelResolved` on ctx) so delegating the choice never hides which tier actually runs. Changing `AI_MODEL_DEFAULTS` to the sentinel affects ONLY devices with no stored choice. **Putting an EXISTING device on auto, without overriding intent.** The earlier change only moved the default, so any device that had ever opened Settings stayed pinned and got none of auto's self-healing. A one-shot mount migration (guard flag `ai-model-auto-migrated`) rewrites a stored id to the sentinel **only when it is a FORMER DEFAULT** (`AI_FORMER_DEFAULTS` + `isFormerDefaultModel`) — i.e. a value the app itself put there, never a deliberate pick. Someone who chose Sonnet or Opus keeps it: silently moving them to the cheapest tier would be the same quiet substitution the alias rules refuse. The guard flag matters as much as the migration — without it, picking the cheapest tier ON PURPOSE after the migration would be flipped back to auto on every launch, for ever. **A liveness probe was also added** (`buildModelProbeRequest`, pure + `probeModel` in the hook, `modelProbe` on ctx): a plain metadata **GET `/v1/models/<id>`** per provider — free, no body, no tokens — fired when the user PICKS a model and from a "Vérifier le modèle" button next to the picker, with the verdict rendered directly underneath. It answers "does this model still exist for my key?" at the moment of choice instead of at the next search, which is the gap that let the Gemini outage run four months. **Only a 404 is a verdict ON THE MODEL** — 401/403/429/5xx report "vérification impossible", because telling the user their model is gone when their key is bad or they are rate-limited sends them changing the wrong setting. A 404 under auto also records the dead model, so the next call already skips it. Note this is NOT the model-LIST endpoint auto deliberately avoids: listing is the wrong tool for CHOOSING a model, but asking whether one specific id exists is exactly what it is right for.

- **Dead-model detection:** a retired model id fails on EVERY call, so surfacing the provider's raw sentence hid the outage for four months (`gemini-2.0-flash`, the app's own Gemini default, was shut down 2026-03-03 and the UI showed "models/gemini-2.0-flash is not found for API version v1beta"). Two pure helpers in `useAiAutoFill.ts`: **`providerError(err)`** builds the thrown Error and keeps the provider's machine-readable code on it as `.providerCode` (`error.type` on Anthropic / `error.code` on OpenAI / `error.status` on Gemini) — Anthropic's retired-model 404 has a message of literally `"model: claude-x"`, so the discriminator is NOT in the text and a message-only detector cannot see it; the DISPLAYED string is unchanged. **`isModelGoneError(e)`** returns true on that code (`not_found_error` / `model_not_found` / `not_found`) or on the message patterns, and `surfaceErr` + the label-scan handler then show `ai_err_model_gone` ("Ce modèle n'est plus disponible… choisissez-en un autre dans Paramètres → IA") instead of the raw text. **A dead model deliberately SKIPS the local-catalogue fallback in `onErr`** — that fallback exists for TRANSIENT failures (timeout, rate limit, network), and a silent catalogue fill would leave the user permanently mis-configured while every non-catalogue blend kept failing unexplained; the catalogue fill stays one tap away on the offer button. **The gap patterns are `.{0,80}`, never `[^.]{0,80}`** — model ids are full of dots (`gpt-5.6`, `gemini-1.5-pro`), and the dot-excluding version could not match a single real message (caught by a test before it shipped). Tested against the three providers' REAL wire messages plus a non-firing list (rate limit, overloaded, bad key, quota, and a catalogue "not found" that has nothing to do with models).
- **Tool:** `web_search_20260209` with `allowed_callers: ["direct"]` (Anthropic built-in, `max_uses: 3`) — only exposed for Anthropic; OpenAI/Gemini use their pre-trained knowledge. The `_20260209` version is the current default per Anthropic; dynamic filtering kicks in on Opus 4.6+ / Sonnet 4.6 only — on Haiku 4.5 (the current default model) it behaves like the older `_20250305` but is kept on the newer string so the day we re-evaluate a smarter model, the tool version is already right. **`allowed_callers: ["direct"]` is mandatory on Haiku 4.5** — without it the API rejects the request with "claude-haiku-4-5 does not support programmatic tool calling", because `_20260209` defaults to requiring PTC. The escape hatch is documented in the rejection message itself. If a future migration moves the default model to Opus / Sonnet, `allowed_callers` can be removed to unlock PTC's token-efficiency gains.
- **Purpose:** Auto-populate tobacco/pipe/wishlist details — for tobaccos and wishlist items: category, cut, blend, Force/Room Note/Taste, `agingMax` (max cellar age, integer or range e.g. `10-15`, empty string if unknown); for pipes: shape, chamber dimensions
- **Source priority (tobacco/wish prompt only):** the system prompt instructs the model to query, in this strict order: (1) `smokingpipes.com` — the **reference for every field** (category, cut, blend / composition, strength, room note, taste, max age, description). The official spec table AND the SP blend description prose are both authoritative; user comments on SP product pages are demoted to "confirmation only". (2) `tobaccoreviews.com` — fallback if SP is missing the info, OR to enrich the description with 1 sentence of aggregated user feedback (must NOT override an SP value). (3) `reddit.com/r/PipeTobacco` — fallback ONLY if SP and TR come up short. The 3-search budget fits exactly: SP + TR + optional Reddit. The SP priority applies to ALL fields, not just Force/RN/Taste as it once did. Pipes don't have a deterministic priority — the prompt just asks for "web search to identify the pipe" since most pipe data lives on a single shop listing.
- **Language:** `langInstr` appended to every system prompt instructs the model to write **all text fields** (description, blend, tasting notes) in the app's active UI language — **every UI language**, not just FR/EN. `LANG_PROMPT_NAME` (module-level in `useAiAutoFill.ts`, shared with `buildScanPrompt`) maps `lang`→English language name; French gets a French clause, every other language gets an English clause that *names* the target language (`"…written in Spanish/German/Italian/European Portuguese"`) so any provider complies. Fallback `LANG_PROMPT_NAME[lang] || "English"`. **It is DERIVED — `Object.fromEntries(LANGUAGES.map(l => [l.code, langAssets(l.code).aiPromptName]))`, not a literal map**, because the literal one silently made the AI write in English for any language added after it (the six-silent-fallback class; `aiPromptName` is a `LANG_ASSETS` column, so doc:check gate 13 fails when a new language has no row). Category/cut are NOT AI-translated — they're stored canonical (French) and localised in-app via `xl()`.
- **Prompt safety:** User query truncated to 200 chars before embedding in prompt to limit injection surface
- **Label scan:** `aiScanLabel(kind, file)` in `useAiAutoFill` — photo of the tin → provider vision request → brand / name (+ blend when readable) filled into the tobacco or wishlist form. Pure helpers exported for tests: `parseScanResult` (JSON extraction + refusal/clip scrub, null when neither brand nor name is readable), `buildScanRequest` (per-provider wire shape — Anthropic base64 image block / OpenAI data-URL image_url / Gemini inline_data; Gemini key in `x-goog-api-key` header, never the URL), `buildScanPrompt`, `redactApiKeys`, `aiClipStr`, `aiIsRefusal` (the last two moved out of the `aiAutoFill` closure so both paths share the scrub). `LANG_PROMPT_NAME` (module-level, shared with the autofill prompt) instructs the scan to write any extracted blend composition in the active UI language via `buildScanPrompt(lang)`. **No `web_search` tool on the scan request** — the answer must come from the image (anti-hallucination). The photo is canvas-downscaled to 1024 px JPEG (q 0.85) before upload and never persisted. Scan overwrites brand/name (the scan IS the user's intent) but fills `blend` only when empty. **Auto-chain:** a successful scan immediately calls `runAutoFill(type, qOverride)` (the extracted body of `aiAutoFill`) with a query built from the SCAN RESULT — not from the form, whose setState hasn't re-rendered yet (stale closure). The spinner stays on across both calls; `parseAndApply` / `onErr` clear it. A failed scan never fires the chained search. UI: `AICard` `onScanFile` prop (hidden `<input type="file" accept="image/*">`, NO `capture` attr so iOS AND Android offer camera + library) — passed by TobaccoFormView + WishFormView only; the pipe form doesn't (stampings too small/worn for reliable extraction).
- **Response sanitisation (extended in 206):** `stripMarkupFromString` (`src/utils.ts`) is the shared scrubber. `clipStr` in `parseAndApply` wraps it for every text field returned by every provider (Anthropic, OpenAI, Gemini). Two passes: (1) strip any HTML-like tag `</?[a-z][^>]*>` while keeping the inner content — Anthropic's web search wraps quoted facts in `<cite index="N-M">…</cite>`, other providers occasionally leak `<span>` etc.; (2) decode the common HTML entities (`&amp; &lt; &gt; &quot; &#39;`). Then collapses orphan whitespace. `migrateData` (utils.ts) calls the same helper on load so pre-dirty data gets cleaned without user action — covered fields: tobacco/pipe/wish/accessory name + brand + blend + description + tastingNotes + notes, and session notes. Tests: `src/__tests__/useAiAutoFill.test.ts` for the live path, `src/__tests__/migrateData.snapshot.test.ts` for the on-load scrub.

- **Catalogue lookup (the catalogue is the USER'S OWN FILE):** the catalogue is checked BEFORE the provider API on every auto-fill, and `"local"` has been the default. ## Scroll preservation

Returning to a list view (Catalogue / Wishlist / Collection / Workshop / Journal) after opening a detail, editing an entry, or adding a new one must restore the list scroll exactly where the user was. The pipeline:

- **`scrollSaveRef`** (App.tsx `useRef<Record<string, number>>`) holds the last-known scrollY per list, keyed by: `inv` (tobaccos + wishlist when statusFilter="wish"), `pipes`, `acc`, `journal`, `wish` (the wishlist *form overlay* opening — distinct from `inv` because it doesn't trigger a view change).
- **Save sites:**
  - `ctxSetDetail` / `ctxSetPipeDet` / `ctxSetAccDet` snapshot the scroll when a detail is opened (list → detail).
  - `nav(v)` snapshots the scroll of the **leaving** view if it's a list (`inv` / `pipes` / `acc` / `journal`) — covers the `+` button and the journal's "edit session" row tap, where no detail intermediate is involved.
  - `InventoryListView` snapshots `scrollSaveRef.current["wish"]` inline at every `setShowWishForm(true)` call site (3 sites) — the wish form is an overlay, not a view change, so neither `nav` nor the detail wrappers fire.
- **Restore sites:**
  - The centralised `useEffect` on `[view, detail, pipeDet, accDet]` in App.tsx restores `inv` / `pipes` / `acc` / `journal` whenever the user lands on the list with no detail open and `scrollToTopRef.current === false`. Forward-nav (default) sets `scrollToTopRef.current = true` so the effect's early-return guard takes over and the user lands at the top — that's the desired behaviour for an intentional menu tap.
  - `useWishStore.updateWish` restores `wish` directly after the form save (no useEffect because the wish form is overlay-only — no view change to watch).
- **`restoreScrollY(targetY, maxAttempts = 20)`** (`src/utils.ts`) — shared helper. Single `requestAnimationFrame` was too early when a list view re-mounts after closing a detail: the first paint shows an empty page and `scrollTo` gets clamped to the still-tiny `scrollHeight`. The helper retries across up to 20 frames (~333 ms) until `document.scrollHeight - innerHeight >= targetY`, then commits the scroll. Capped so a legitimately shorter list (item deleted / filter changed) doesn't loop forever.
- **Bottom dock tap-active-tab = scroll to top (iOS-style):** `CuratorApp` `onNav` handler checks `id === dockId` and forces `requestAnimationFrame(() => window.scrollTo(0, 0))` when the user taps the tab they're already on. Without this, `nav()` doesn't change `view`, the restore `useEffect` doesn't fire, and the dock tap was a no-op.
- **`nav()` must NOT wipe `scrollSaveRef`:** the previous `scrollSaveRef.current = {}` at the end of `nav` silently killed the `restoreScroll: true` path used by every store (useTobaccoStore / usePipeStore / useAccessoryStore / useSessionStore) on save success. Keys are per-list so they don't interfere; forward-nav clears via `scrollToTopRef`, not by wiping.
- **`nav()` must skip the scroll snapshot while a detail panel is open:** for a time, `nav()` snapshotted `window.scrollY` into `scrollSaveRef` whenever the LEAVING view was a list — but if a detail panel was open (`detail` / `pipeDet` / `accDet` set), the scrollY belonged to the detail (which scrolled to top on open), not the underlying list. Tapping Edit from a detail therefore overwrote the position saved by `ctxSetDetail` / `ctxSetPipeDet` / `ctxSetAccDet` with 0, and the post-save restore landed at the top. The fix gates the four snapshot lines behind `!detail && !pipeDet && !accDet`. Regression locked by `src/__tests__/navScrollGuard.test.ts`.

**`history.scrollRestoration` is `'manual'`, set in `main.jsx` before React mounts.** Reported from the app: open a blend in the catalogue, close it with a left-edge **swipe**, and you land at the TOP of the 1222-row list; the × and Escape are fine. **It is not the app scrolling.** Traced in a browser: `window.scrollTo` is never called, the document never shrinks (75 030 px and 1222 rows throughout), and `Modal`'s focus restore lands on the right row with the scroll still intact at 12 000 — the jump happens AFTER every handler has run. That is the browser restoring the position recorded on the history entry being returned to, and `useBackNavigation` seeds that entry at mount, when the scroll is 0. The app already owns this (`scrollSaveRef` + `restoreScrollY` for the restore paths, `scrollToTopRef` for forward nav), so the browser doing it too is a straight conflict — and the browser wins because it acts last. **That is also why the defect is invisible almost everywhere**: most back paths navigate to a view whose scroll the app then restores explicitly, painting over the browser's 0; the catalogue merely closes a modal, so nothing re-scrolls and the 0 stands. **It MUST be set pre-mount**: `scrollRestoration` is a property of the CURRENT history entry, so setting it later leaves the entry you navigate BACK to on `'auto'` and changes nothing — measured, and it briefly looked like a refutation of the diagnosis. Feature-detected + try/catch, because the pre-mount block also seeds the theme and the language and must not abort. Locked by `scrollRestoration.test.ts` (source-level: jsdom implements neither scroll nor `scrollRestoration` semantics), which also asserts that `useBackNavigation` does NOT set it — two owners of a per-entry property is how this returns — and that nothing in `src/` sets it back to `'auto'`.

When adding a new list view: snapshot the scroll on every "leave" path (detail open + `+` button + any overlay form opening that isn't a view change), restore it via the centralised `useEffect` (add a new branch keyed by `view === "newlist"`), and pair store add/update success calls with `nav("newlist", { restoreScroll: true })`.

## Back navigation & gestures

The system-back inputs (browser/hardware back, left-edge swipe) call a single `goBack()` routine. **`goBack` is now a DYNAMIC back stack, not a fixed parent-mapping.** The earlier code hard-coded ONE parent per screen (every non-form view → home), so system-back / edge-swipe from Stats or the session form teleported to Home instead of the actual previous screen. It now tracks a real history STACK of visited screens so back returns to where the user truly came from.

**Split of responsibility:**
- **`src/utils/navHistory.ts`** — the PURE engine (exhaustively unit-tested by `navHistory.test.ts`): `NavLoc` (a screen snapshot = `view` + open `detailId`/`pipeDetId`/`accDetId` + `statusFilter`), `pushLoc(stack, leaving)` (immutable push; de-dups the top; caps depth at 40), `isFormView`/`isRestorable`/`isBareRoot`/`sameLoc`/`locIdentity`, `fallbackParent(view)` (the minimal old mapping for an empty stack), and **`decideBack(state)`** — THE routing decision as a pure function returning a `BackAction` (`close-detail`/`close-pipe`/`close-acc`/`close-wish`/`pop`/`nav`/`none`). **`pushLoc` skips non-restorable locations: forms, `tasting`, AND bare dock/main pages** (`NAV_ROOT_VIEWS` = home/inv/pipes/acc/journal/stats with NO fiche open). **Per user request: NO history between main pages** — the dock tabs are siblings under Home, not a linear stack, so leaving one is never recorded and back from any main page falls through to Home (`fallbackParent`). A dock view WITH a fiche open is a DRILL state (`detailId` set), which IS restorable — so `detail → edit → back` still returns to the fiche, and `form → back` returns to its list via `fallbackParent`. **Critical fix: `nextStackOnNav(stack, target, leaving)` RESETS the stack whenever nav() lands on a main/root page** — a dock tab is a root, not a history cran. Without this, navigating away from an OPEN fiche via a dock tab pushed the fiche as a drill state, so back from ANY later main page dumped the user onto that stale fiche ("back always returns to accessories"). - **`src/hooks/useBackNavigation.ts`** — TRANSPORT only now: takes a single `onBack` callback, installs the `popstate` + edge-swipe listeners once, seeds `history.replaceState`+`pushState` on mount, 400 ms debounce, and calls the latest `onBack` via a ref. No routing logic.

Forms + `tasting` are never a back TARGET (filtered by `pushLoc`). A drained stack falls back to `fallbackParent` (forms→their list, else→home), so the first taps of a fresh session still behave. - `nav(v)` — default forward navigation. Snapshots the leaving view's scroll if it's a list (`inv` / `pipes` / `acc` / `journal`), sets `scrollToTopRef.current = true`, then updates `view`. The centralised restore useEffect sees the flag and lets the page land at the top.

## Google Identity Services — lazy script load

The `gsi/client` script is **NOT** loaded from `index.html`. `useGdriveSync.ts` injects it on demand the first time the user triggers a Drive action (or the silent-refresh effect fires 2.5 s after mount when an auto-save fid exists). Cold-start cost is therefore zero. Two call sites: the silent token refresh effect (`useEffect` mount path) and `gdriveGetToken` (interactive). Both check `window.google?.accounts?.oauth2` first and skip the injection if the script is already there. CSP `script-src` still whitelists `accounts.google.com` so the lazy load is allowed.

No Subresource Integrity (SRI) is pinned: Google publishes the script at an unversioned URL and rolls updates on their own cadence, so a pinned hash would brick Drive auth at every Google update. Defense-in-depth instead: HTTPS-only, CSP, and a narrow `connect-src` (the script can only call out to whitelisted domains). JSZip on cdnjs IS pinned with SRI because it ships at a versioned URL.

## Optional Drive backup encryption — Phase 1

Users who want their Drive backups unreadable to a third party (e.g. a Google account compromise, a casual viewer with delegated access to the `appDataFolder`) can opt into AES-GCM-256 encryption with a user-chosen passphrase.

**Architecture**:
- `src/utils/cryptoBackup.ts` — pure crypto module. `encryptBackup(json, passphrase)` returns a JSON-stringified envelope `{ _encrypted: "v1", _kdf, _cipher, salt, iv, ciphertext }`. `decryptBackup(envelopeJSON, passphrase)` returns the plaintext. `isEncryptedEnvelopeJSON(s)` is the cheap "does this look encrypted?" detector used by the restore path — fast-rejects via `indexOf("\"_encrypted\"")` before parsing. **No size cap.** The original 2 MB short-circuit was removed because encrypted backups containing photos easily exceed 2 MB (photos are base64-embedded inside the plaintext, then the whole thing is base64-wrapped again as ciphertext), and the cap silently downgraded such envelopes to the "plaintext" branch of the restore path → `JSON.parse` succeeded → no `.tobaccos` field → user saw "Fichier invalide". Don't re-introduce the cap; the indexOf prefix check is the cheap rejection for plaintext backups already.
- Web Crypto API (no third-party dep). PBKDF2-SHA256 600 000 iterations (OWASP-2023 floor). AES-GCM-256 with random 12-byte IV + 16-byte salt per encryption — same passphrase + same plaintext = different ciphertext every time.
- `src/views/curator/EncryptionPromptModal.tsx` — passphrase prompt UI. Two modes: `setup` (enter + confirm + warning) and `unlock` (single field).
- `src/hooks/useGdriveSync.ts` — `maybeEncryptPayload` wraps the save path, `maybeDecryptText` wraps the restore path. Plaintext backups still flow through both unchanged (envelope detection branches per call).

**State (App.tsx)**:
- `driveEncryptionEnabled` — persistent flag in `localStorage["cave-drive-encryption-enabled"]`. Survives reloads. Cleared explicitly by the user via the Settings toggle.
- `drivePassphrase` — **memory only** (`useState`), never persisted. Lost on reload. The user re-enters it via the unlock modal on next Drive operation.
- `encryptionPrompt` — ephemeral `{ mode, resolve }` pair; `EncryptionPromptModal` reads it and calls `resolve(pw | null)` on submit / cancel.

**UX flows**:
- **Enable encryption**: Settings → Drive section → toggle "Encrypt Drive backups" ON → setup modal (passphrase + confirm + warning) → on submit, flag saved + passphrase cached in memory.
- **Disable encryption**: toggle OFF → `window.confirm` → flag cleared, passphrase cleared. Old encrypted backups remain restorable with the passphrase; new saves are plaintext.
- **After a reload (flag ON, passphrase gone)**: Settings shows a warn Notice "🔒 Encryption active · passphrase needed" with an "Enter passphrase" button. The next manual save also prompts.
- **Manual save** (`gdriveSave`): if flag ON and no passphrase cached, prompts. On cancel, the save aborts cleanly (no upload).
- **Auto-save** (`gdriveSaveQuiet`): if flag ON and no passphrase cached, **skips silently**. The auto-save resumes the next time the user unlocks via Settings or via a manual save. This avoids surprising the user with an auto-popup while editing.
- **Restore** (`doGdriveConfirm`): downloads the file, detects envelope via `isEncryptedEnvelopeJSON`, prompts if needed, decrypts, then routes through the normal merge/replace picker.

**What this protects**:
- ✅ Drive backups are opaque to anyone who reads them without the passphrase.
- ✅ AES-GCM tag verification catches any tampering (ciphertext + envelope metadata).
- ✅ Per-backup random salt + IV — no replay analysis across multiple backups encrypted with the same passphrase.

**What this does NOT protect**:
- ❌ Local data in `localStorage` / IndexedDB stays plaintext (the user already trusts the device; encrypting locally would block every read of the entire app).
- ❌ The OAuth token to access Drive is still stored unencrypted in `sessionStorage` (non-iOS) / `localStorage` (iOS standalone) — a malicious script with same-origin access could still upload garbage. CSP locks down `script-src` precisely to prevent that.
- ❌ **Forgotten passphrase = lost backups.** There is no recovery. The setup modal warns clearly and the user must confirm before enabling.

**Out of Phase 1** (would be Phase 2 if requested):
- JSON / CSV / ZIP local exports — currently plaintext, regardless of the Drive encryption flag.
- "Change passphrase" flow.
- Persistent "session unlocked" indicator outside Settings (currently visible only when the user opens the modal).
